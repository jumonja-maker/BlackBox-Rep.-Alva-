## Для обычного пользователя

BLACK.BOX работает самостоятельно без Alva, интернета, API-ключей,
туннелей и модификации чужих программ. Все наблюдения сохраняются
в SQLite/HTML/JSON и стандартном `ai-handoff.json`. В приложении
**Alva Lab** явно обозначено, что это самостоятельный отчёт, а
не свидетельство запуска библиотеки Alva.

## Для пользователя с доступом к настоящей платформе Alva

1. Получить Alva легально через владельца частного репозитория и
   установить её в отдельное локальное Python 3.11+ окружение.
   Не переносить исходники/wheel в публичный BLACK.BOX или CI.
2. В **Alva Lab** нажать **CONNECT EXTERNAL ALVA / ПОДКЛЮЧИТЬ ALVA**
   и выбрать `python.exe` именно из этого окружения.
3. BLACK.BOX один раз проверит, что через выбранный Python реально
   выполняются три scoped-операции платформы. Сохранит путь к
   интерпретатору только после удачного рукопожатия.
4. При завершении следующего наблюдения фоновый worker автоматически
   проверит уже закрытый локальный сеанс и создаст рядом с отчётами
   **`alva-diagnostics.json`**. Если Alva не работает, явно сохранит
   отказ (стандартные отчёты останутся целыми).
5. Кнопка **DISCONNECT / ОТКЛЮЧИТЬ** прекращает будущие вызовы.

Это локальный subprocess, запускаемый без PowerShell, Git, HTTP
сервера, сокетов и туннеля: `python.exe -I -u alva_sidecar_worker.py`.
Работник встраивается только как **открытый код адаптера BLACK.BOX**,
с помощью флага PyInstaller `--add-data`. Сама Alva ни в каком
виде не упаковывается в публичный EXE.

## Что Alva реально проверяет

Компоненты `blackbox.observer.samples`,
`blackbox.observer.lifecycle` и `blackbox.observer.errors`.
Каждый регистрируется в настоящем `ComponentHost`, разрешается
напрямую scoped route и исполняется один раз через
`invoke_adapter_checked`. Принимаются только
`RESPONSE_AVAILABLE / CHECK_ACCEPTED / SCOPE_ONLY` и
валидная Alva AI Handoff. Любое несоответствие — явная ошибка.

В рабочий процесс передаются исключительно:

- количество выборок и число ошибок наблюдателя;
- наличие измерений памяти/CPU (не вся сырая последовательность);
- числовые peak memory / CPU для локальной проверки полноты;
- конечный статус сеанса (COMPLETED, INTERRUPTED, ...).

Субпроцесс не получает PID, имя процесса, абсолютные пути,
исходные документы, содержимое памяти, stderr, пароли или
соединение с API чата. Отчёт не разрешает ИИ никаких действий.

**Ничего этого недостаточно для определения истинной строки
ошибки в чужом EXE.** Проверяются границы собственных
компонентов BLACK.BOX и согласованность предоставленных сведений,
а не внутренняя логика целевого приложения.

## Безопасность и границы происхождения

Путь Python пользователь выбирает явно; запуск произвольной
сторонней программы с правами пользователя опасен. Выбирать
можно только **доверенное** и уже авторизованное окружение.
Проверка API и даже успешный ComponentHost **не доказывают
Git-коммит или происхождение пакета**: флаг
`alva_origin_authenticated=false`. Владельцу Alva необходимо
отдельно проверить SHA коммита и установочный wheel SHA-256.

Запускается изолированный Python `-I`, очищаются переменные
`PYTHONPATH`, `PYTHONHOME`, `PYTHONSTARTUP`, `PYTHONINSPECT`,
отключён stdout/произвольный stderr, установлен тайм-аут 20 с
и ограничение размера JSON. Это **не sandbox безопасности**
для заведомо вредоносной установленной платформы.

Без подтверждения установки пользователем **нет скрытых импортов Alva
и нет запуска её кода**, даже после наблюдения.

## Отношение к первому GitHub Release

Кандидат **v0.3.0** — первая публичная версия универсального
наблюдателя с реальным *опциональным подключением* Alva, а
не гарантия, что сам EXE содержит Alva или что Alva всегда работает.

Бесплатная версия без Alva остаётся полностью пригодной для
мониторинга и отчётов. Перед переносом в `main` и публикацией
тегированного GitHub Release требуются PASS CI для **точного HEAD**,
ручная проверка обновления/удаления и решение по статусу
preview vs stable. До этого использовать Draft PR и артефакт CI.
