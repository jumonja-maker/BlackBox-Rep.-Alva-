# BB-WAVE-02 / R40 — события аварий и сохранённые дампы

R40 расширяет существующие Application Event Log, Deep Inspection и
Investigation Engine 3. Новый отладчик или отдельная база доказательств
не создаются. Фактическую приёмку определяет GitHub CI точного коммита.

## Windows Event Log и WER

crash_events.query читает Application Error 1000, Windows Error Reporting
1001 и .NET Runtime 1026 в ограниченном UTC-интервале. Execution.ProcessID
обозначает процесс, записавший событие, и не заменяет PID аварийного приложения.

Событие относится к PID только при наличии именованного поля payload.
expected_created_100ns позволяет сравнить исходный creation FILETIME с
записанным ProcessCreationTime. Несовпадающий экземпляр отбрасывается.
Без времени рождения сохраняется BIRTH_NOT_ATTESTED.

У WER 1001 часто нет PID. При явно выбранном имени образа такие записи
показываются отдельно как wer_candidates: совпадение имени и времени
не доказывает принадлежность выбранному процессу. Они не становятся
автоматическим подтверждённым crash-trigger R50.

Отсутствие события не доказывает отсутствие аварии: журнал может быть
задержан, недоступен или отключён. R40 не меняет настройки WER/реестра.
Сохраняются ограниченные имена образов/модулей, версии и числовые коды;
исходные сообщения и произвольный payload не экспортируются.

## Сохранённый minidump

Существующая операция dump_inspect проверяет MDMP, директории, модули,
потоки, диапазоны, размер и SHA-256 открытого файла. Добавлены
ExceptionStream и creation FILETIME из ThreadInfoList, когда они
присутствуют и не помечены ошибочными.

Для аварийного потока предпочтителен сохранённый Exception CONTEXT:
ThreadList CONTEXT может уже относиться к обработчику исключения.
Без unwind показывается только CAPTURED_CONTROL_CONTEXT_PC_ONLY.

Полный диапазон записанного CONTEXT проверяется, но native-анализ читает
только реальный базовый AMD64 prefix 1232B. Исходные размер и flags сохраняются;
trailing/XSTATE bytes помечены EXTENSIONS_NOT_ANALYZED. Во временной native
копии снимается только XSTATE flag0x40; расширенные регистры не выдумываются.

SHA-256 подтверждает выбранные байты, но не удостоверяет производителя.
PID и секундное creation time из MiscInfo не заменяют live-идентичность.
live_process_binding остаётся NOT_ESTABLISHED.

Ограничения: файл до 2 ГиБ, структурные чтения до 8 МиБ, общий deadline
операции до 15 секунд, ограниченные количества streams/records и строк.
Повреждение, неоднозначная память, отмена и deadline не превращаются
в успешный полный результат.

## Стеки AMD64 и локальные символы

Для явного анализа выберите дамп, соответствующий локальный PE и при
необходимости PDB. В существующую dump_inspect передаются image_path,
pdb_path и max_frames (1–128). Прямой API — deep_dump.unwind_dump.

На Windows используется настоящий DbgHelp StackWalk64. Стек и обычные данные
читаются только из захваченных диапазонов, которые имеют приоритет. До загрузки metadata проверяются сохранённые
RSDS GUID/age, timestamp и размер образа; локальный PE закреплён от изменения.
Автоматической загрузки по путям из дампа, symbol-server или чтения текущей
памяти процесса нет.

Если диапазон действительно отсутствует в dump, разрешено читать из явно
выбранного закреплённого PE только file-backed headers, Exception Directory
и точные UNWIND_INFO spans, выведенные из проверенных RUNTIME_FUNCTION.
Отдельный cursor не меняет позицию DbgHelp hFile. SHA-256 вычисляется именно
для этого открытого файла и сравнивается с local_image role manifest и PE
источником PDB. Источник помечен LOCAL_PINNED_PE_UNWIND_METADATA, отдельно от
captured memory. Writable/code/другие readonly данные, gaps и virtual tails не
подставляются; неоднозначный или частичный captured диапазон не заменяется.

Непроверенный следующий модуль или отсутствующая память останавливают
unwind. Полнота стека не заявляется: результат остаётся частичным.
Это не RBP-сканирование и не универсальный WinDbg.

Если освобождение SymCleanup не подтверждено, сохраняются собственные
session HANDLE и закреплённый PE; новый unwind блокируется. Явный
retry_cleanup=True в существующей dump_inspect повторяет только очистку,
не чтение дампа или native-анализ. Неопределённый CloseHandle не повторяется
по одному числовому значению. Поле offline_owner_retained относится только
к этому владельцу; оно не очищает и не подменяет состояние R10 Helper.

Имена функций и C13-строки происходят из существующего локального PDB reader
с его статусами неоднозначности, inline/OMAP и отсутствующих данных.
Строка в PDB не означает чтения или аутентификации исходного кода.
Универсальный managed heap/CLR DAC-анализ не добавляется; доступный
EventPipe/CLR остаётся отдельным существующим источником.

## Investigation и приватность

Проекция blackbox.crash-investigation/1 читает существующий граф.
События, дампы, модули, потоки и кадры сохраняют node/source/hash references.
Записанное исключение или имя модуля не устанавливают внутреннюю причину:
root_cause остаётся UNKNOWN.

Источник Investigation DUMP_METADATA принимает явно выбранные image_path и
pdb_path. Дамп, PE и PDB входят в ролевой content_manifest с отдельными
SHA-256 и повторной проверкой неизменности. Нормализованное представление
использует постоянный предел 64 кадров; произвольный max_frames источника
отвергается, чтобы разные представления не получили одну идентичность.

case.crash_investigation вычисляется рабочим потоком при создании, сохранении,
экспорте и чтении собственного SQLite-индекса из записанных узлов. Повторное
чтение не открывает исходный дамп, PE или PDB и не повторяет native-анализ.
JSON/HTML сохраняют это представление, HTML также содержит таблицы для
чтения человеком. Сохранённый корректный формат не удостоверяет подлинность
доказательств или заявленную причину.

RunReceipt отделяет закрытие файлов источников от фактической очистки
offline DbgHelp. Подтверждение ресурсов сохраняется только после успешных
SymCleanup, освобождения закреплённого PE и закрытия session HANDLE;
исключение RECOVERY_UNCONFIRMED не превращается в подтверждённую очистку.

Проекция, JSON/HTML и обычный share содержат метаданные. Байты памяти,
содержимое дампа, параметры исключения и полные локальные пути автоматически
не добавляются. Явное приватное dump_read_memory остаётся отдельной операцией.

Форматные fixtures проверяют повреждения и отрицательные случаи; реальная
Windows-приёмка отдельно требует собственного аварийного процесса,
настоящего MiniDumpWriteDump с ExceptionPointers, независимого кода/TID/RIP,
настоящего unwind/PDB, normal-exit контроля, экспорта/read-back и cleanup.
Физический UAC и домашние Windows 10/11 не выдаются за проверенные
на hosted runner.
