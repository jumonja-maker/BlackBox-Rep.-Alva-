**BLACK.BOX — концепция исследовательского инструмента и требования к готовому продукту**

Версия 1. Документ объединяет обсуждённые цели и инженерные предложения. Это описание целевого продукта, а не подтверждение реализации перечисленных функций в текущей версии. Исходный заказ BB-DI-001 и его обязательные критерии сохраняются; новые идеи следует согласовать с ними, исключив дублирование.

**1. Назначение**

BLACK.BOX — локальный инструмент для исследования поведения Windows-приложений. Пользователь выбирает программу, воспроизводит интересующее действие или сбой и получает связанную запись: что происходило, когда, с каким процессом и потоком, откуда получены данные и насколько полна картина.

Главный пользовательский результат — пригодное для инженерной работы исследование конкретной проблемы. Его можно самостоятельно изучить, передать разработчику или чату, дополнить следующей записью и использовать для проверки исправления.

«Жить внутри программы» в этой концепции означает тесно связывать внешние наблюдения с внутренними событиями, которые программа действительно предоставляет. Для собственной программы глубина повышается через символы, диагностические интерфейсы среды исполнения и явную инструментализацию. Один и тот же продукт должен поддерживать доступное внешнее наблюдение за сторонним приложением.

Существование внешнего наблюдателя не даёт автоматического доступа к смыслу внутренних очередей, объектам каждого языка и всем причинам ошибок. Расширение доступа должно опираться на конкретный механизм сбора и проверяемый источник.

**2. Почему пользователь может выбрать BLACK.BOX**

Предлагаемое конкурентное преимущество — удобная связка воспроизведения, доказательств и повторной проверки. Это гипотеза о ценности продукта, которую нужно подтвердить работающими сценариями и сравнением с существующими средствами.

Process Monitor уже предоставляет подробную запись файловых операций, реестра, активности процессов и потоков, включая стеки. Windows Performance Analyzer анализирует трассы ETW. Поэтому наличие счётчиков и трассировок само по себе не доказывает преимущество BLACK.BOX. [S1, S2]

Приоритетные особенности BLACK.BOX:

- Исследование организовано вокруг конкретного действия и проблемного интервала.
- Подготовка собственной программы сопровождается проверкой фактически получаемых данных.
- Каждый вывод связан с наблюдениями; пробелы и ограничения видны в интерфейсе и экспорте.
- Повторный эксперимент помогает проверить исправление.
- Переносимый пакет пригоден для чтения человеком и обработки программой или ИИ.

Проверять пользу следует на одинаковых задачах: сколько требуется действий и времени для получения пригодного отчёта, удалось ли сохранить важные доказательства, не появилось ли ложное объяснение.

**3. Два режима прав**

Уровень прав и глубина инструментализации — отдельные свойства сеанса.

| Вопрос | Без повышения прав | С правами администратора |
| --- | --- | --- |
| Основной сценарий | Наблюдение за доступными приложениями пользователя | Расширение доступа там, где это позволяет Windows |
| Процессы и счётчики | Сбор доступных данных с явными отказами по остальным | Дополнительные доступные процессы и операции |
| Системные источники | Только реально доступные с текущими правами | Дополнительные трассы и провайдеры при успешном включении |
| Внутренние события своей программы | Доступны при поддержке приложения и среды исполнения | Также зависят от поддержки приложения и среды исполнения |
| Честность отчёта | Обязательна | Обязательна |
| Гарантия полной видимости | Определяется реальными источниками | Также определяется реальными источниками |

Права проверяются для каждой операции. Windows различает права чтения памяти, запроса информации и другие права; защищённые процессы имеют отдельные ограничения. Повышение прав не следует показывать как обещание абсолютной видимости. [S3]

Практический интерфейс: пользователь видит, какой датчик недоступен и что может изменить повышение прав. Уже записанный материал сохраняется. Если для продолжения нужен перезапуск помощника или новый сеанс, программа явно обозначает границу записей.

Разумная реализация — обычный GUI и ограниченный привилегированный помощник для необходимых операций. Его команды, целевые процессы и жизненный цикл должны быть определены явно. Это предлагаемая архитектура, а не утверждение о текущем устройстве BLACK.BOX.

**4. Глубина исследования**

| Уровень | Содержание | Что определяет доступность |
| --- | --- | --- |
| Внешнее наблюдение | Процессы, ресурсы, потоки, доступные сведения об окнах | Windows API и права на цель |
| Системная трассировка | Временные события поддерживаемых провайдеров | Наличие провайдера, права и параметры трассы |
| Своя программа | Этапы операций, очередь заданий, исключения, внутренние идентификаторы | Реальная инструментализация приложения |
| Подробный снимок | Стек, дамп или специальный профиль в выбранный момент | Поддерживаемый механизм, права, символы и выбранные параметры |

Эти уровни могут сочетаться. Детальный сбор включается осознанно: видны состав данных, предполагаемые расходы и возможное влияние на цель. Пользователь должен получать доступ к реализованным исследовательским возможностям без искусственных продуктовых ограничений.

Для функций, способных приостановить процесс или сохранить содержимое памяти, интерфейс коротко объясняет последствия перед действием. Настройки можно сохранить в профиле исследования. Сама запись и анализ должны работать локально; загрузка символов или другие сетевые операции являются отдельными видимыми возможностями.

**5. Основной законченный сценарий**

1. Пользователь выбирает уже запущенную программу либо запускает её через BLACK.BOX.
2. Программа показывает доступность датчиков, идентификатор цели и режим записи.
3. Пользователь задаёт название сценария, например «Сохранение большого проекта».
4. Запускается запись. При необходимости используется заранее ограниченный кольцевой буфер для предыстории.
5. Пользователь выполняет действие и отмечает проблему. Инструментированное приложение может передать собственные границы действия.
6. После остановки BLACK.BOX формирует эпизод с общей шкалой времени.
7. Пользователь раскрывает наблюдения, ограничения и возможные объяснения.
8. Сохраняет переносимый пакет.
9. После изменения приложения повторяет сценарий и сравнивает результаты.

Ключевое требование: проблема должна проходить этот путь в собранном EXE. Наличие работающих отдельных модулей ещё не подтверждает готовность сценария.

**6. Что исследовать**

| Область | Какие данные нужны | Правило интерпретации |
| --- | --- | --- |
| Жизненный цикл | Запуск, завершение, дерево процессов, идентичность экземпляра | PID связывается со временем запуска; повторное использование PID учитывается |
| CPU | Процесс и доступные потоки, накопленное время и интервальные значения | Единицы и нормализация по ядрам указаны явно |
| Память | Доступные показатели working set, private memory, другие поддерживаемые метрики | Рост показателя обозначается как наблюдение, не автоматически как утечка |
| Потоки | Появление, завершение, CPU, доступные состояния и стеки | Отказ чтения не превращается в пустой успешный результат |
| Дескрипторы | Количество и доступные категории | Рост требует проверки причин и возврата после операции |
| Ввод-вывод | Счётчики и поддерживаемые события операций | Байты ввода-вывода процесса не равны физической загрузке диска |
| Окно | Доступные признаки отзывчивости и интервалы проверок | Задержка проверки отделяется от доказанной причины зависания |
| Ожидания | Поддерживаемые цепочки ожидания | Область покрытия механизма указана |
| События приложения | Начало и конец этапов, очередь, идентификатор задания, ошибки | Источник должен реально передавать такие события |
| Завершение и сбои | Код выхода, доступные сведения об исключении, выбранные снимки | Неизвестная причина остаётся неизвестной |
| Контекст системы | Версия ОС, CPU, RAM, архитектура, сопутствующая нагрузка | Контекст нужен для оценки сопоставимости экспериментов |

WCT предоставляет цепочки ожиданий для определённых механизмов синхронизации. Он полезен для исследования зависаний, но не покрывает произвольную логику ожидания приложения. Microsoft также различает синхронные блокирующие и асинхронные отменяемые сеансы WCT. [S4]

Сетевые, GPU- и другие специальные данные следует расширять отдельными датчиками с собственной приёмкой. Наблюдение за сетевыми соединениями само по себе не раскрывает содержимое зашифрованного обмена.

**7. «Подготовить мою программу»**

Мастер подготовки должен давать инструкции, подходящие конкретному приложению, и проверять их результат.

Последовательность:

1. Определить доступные сведения о среде исполнения и сборке. Если определение ненадёжно, показать неопределённость и дать уточнить среду.
2. Показать уже доступные данные.
3. Объяснить, что даст каждый следующий способ подключения.
4. Предложить точные инструкции для поддерживаемой среды.
5. Проверить подключение контрольным событием или тестовым действием.
6. Сохранить проверенный профиль с версиями приложения, адаптера и настройками.

Примеры профилей — направления реализации, а не заявление о готовой поддержке:

| Программа | Подготовка | Возможное дополнение к наблюдению |
| --- | --- | --- |
| Нативная Windows-программа | Подходящие символы; при необходимости собственные события | Имена функций, дополнительные этапы операций |
| .NET | Поддерживаемый диагностический интерфейс, EventPipe/EventSource | События runtime и приложения |
| Python | Явные события действий, журналы и поддерживаемые средства диагностики | Этапы Python-кода и доступные сведения об ошибках |
| Electron / Chromium | Поддерживаемая трассировка и сведения о процессах | Связь активности процессов с событиями приложения |
| Другая среда | Общий формат структурированных событий | Семантика операций без обещания универсального профилировщика |

Символы помогают интерпретировать адреса и функции; соответствие символов бинарной сборке имеет значение. Они не добавляют отсутствующие пользовательские события. [S5]

Для .NET EventPipe позволяет получать события runtime и EventSource; его область отличается от системной ETW-трассировки. Это пример того, почему поддержка среды исполнения должна быть явной. [S6]

Минимальный формат собственных событий BLACK.BOX должен описывать: версию схемы, время и его основание, процесс/поток, тип события, идентификаторы операции и родительской операции, статус и ограниченные по размеру атрибуты. Время получения события хранится отдельно от времени, заявленного источником.

Встроенный API приложения, команда Runner или помощник, которому уже разрешено выполнять действие, могут передавать начало и окончание операции. Универсальное нажатие кнопок во всех программах не требуется для первого законченного сценария.

**8. Время и точность**

Необходимо различать три способа определения границ:

- Ручная отметка отражает момент команды пользователя и включает задержку его реакции.
- Автоматический внешний запуск отражает границы, наблюдаемые управляющим средством.
- Событие приложения отражает точку, в которой оно само зарегистрировало этап.

Микросекундная отметка времени не делает ручной замер микросекундно точным.

Для длительности нужен подходящий монотонный источник времени. Windows предоставляет QPC для измерения интервалов; связь с календарным временем — отдельная задача. [S7]

В сеансе должны сохраняться тип часов, масштаб, точки сопоставления с UTC и ограничения синхронизации. События из разных источников нельзя выстраивать в ложный точный порядок, если неопределённость превышает разницу их отметок.

**9. Доказательность выводов**

Каждая карточка исследования разделяет:

| Уровень | Пример допустимой формулировки |
| --- | --- |
| Измеренный факт | «Показатель private memory вырос на указанном интервале» |
| Наблюдаемая связь | «Во время отмеченного действия вырос ввод-вывод процесса» |
| Гипотеза | «Стоит проверить ожидание операции записи; текущих данных для причины недостаточно» |
| Пробел | «Стек потока получить не удалось: отказ доступа» |

Для вывода сохраняются ссылки на события или диапазоны выборок, идентичность цели, использованное правило анализа и ограничения.

Правила обязательной осторожности:

- Высокий CPU не доказывает бесконечный цикл.
- Низкий CPU не доказывает ожидание диска.
- Рост памяти не доказывает утечку объектов.
- Молчание журнала не доказывает отсутствие операции.
- Совпадение по времени не устанавливает причинность.
- Цикл ожидания интерпретируется в пределах возможностей источника.
- Отсутствие зафиксированной ошибки не равно подтверждению исправности.

Численный «процент уверенности» допустим только при определённой и проверенной методике. Для начала полезнее объяснение оснований и границ вывода.

**10. Повторные эксперименты и сравнение**

Сравнение должно учитывать версию приложения, входные данные, параметры операции, профиль датчиков, уровень прав и существенные отличия среды.

Пользователь задаёт повторения. Программа сохраняет каждый результат, отдельно отмечает прогрев, отмены, ошибки и случаи невоспроизведения проблемы.

Полезные показатели: длительность действия, разброс, медиана, наблюдаемые пики и изменения ресурсов. Перцентили показываются с числом измерений и оговорками; несколько повторов не дают надёжной оценки редких задержек.

Нельзя автоматически объявлять улучшение, если изменились входные данные, состав датчиков или другие существенные условия. В таком случае сравнение остаётся доступным, но получает отметку ограниченной сопоставимости.

Автоматизация повторений поддерживается через конкретные адаптеры, команды или API. Для неподдерживаемого приложения сохраняется ручной сценарий с честными границами времени.

**11. Здоровье самого наблюдения**

BLACK.BOX должен собирать сведения о собственной работе:

- CPU и память своих компонентов.
- Размер и темп записи.
- Заполнение очередей и задержку записи.
- Задержки и пропуски опроса.
- Известные потери событий.
- Отказы доступа и сбои датчиков.
- Изменение профиля во время сеанса.
- Перезапуск помощников и границы неполной записи.

Нужно различать «источник сообщил нулевые потери» и «источник не предоставляет счётчик потерь». Это разные состояния.

Наблюдение само влияет на систему. Измерение ресурсов BLACK.BOX показывает его прямые расходы, но не исчерпывает влияние включённой трассировки на исследуемую программу. Для оценки влияния нужны сопоставимые прогоны без записи, с базовой записью и с подробной записью.

Во время перегрузки можно предложить более лёгкий профиль или применить заранее выбранное пользователем правило. Любое изменение отмечается на шкале времени.

**12. Переносимый пакет исследования**

Предлагаемый логический состав:

| Составляющая | Назначение |
| --- | --- |
| manifest.json | Версии, идентификаторы, состав, контрольные суммы и полнота |
| observations.sqlite | Сохранённые структурированные наблюдения и индексы |
| incidents.json | Эпизоды, отметки, операции и ссылки на доказательства |
| capture_health.json | Доступность датчиков, пропуски и ошибки записи |
| report.html | Автономный отчёт для чтения |
| report.json | Версионированное представление для программ и чатов |
| Необязательные исходные артефакты | ETL, nettrace, журналы, снимки и другие реально полученные материалы |

Это логическая структура: существующие форматы BLACK.BOX следует использовать, если они удовлетворяют требованиям, без ненужного дублирования данных.

Большие исходные материалы могут храниться отдельно с явной ссылкой и отметкой отсутствия в переносимом пакете. Полный архив и сокращённый пакет должны различаться по статусу.

Контрольные суммы подтверждают целостность байтов относительно манифеста. Они не доказывают достоверность датчика, отсутствие ошибок анализа или подлинность источника.

Экспорт должен открываться на другом ПК без установленной исследуемой программы. Проверяются ссылки на доказательства, версии схем и возможность повторного анализа. Исходная запись сохраняется неизменной; исправленный анализ получает отдельную версию.

Перед передачей пользователь видит состав пакета. Журналы, пути и снимки могут содержать чувствительные данные; исключения или обезличивание отражаются в манифесте.

**13. Производительность и устойчивость**

Предлагаемые инженерные требования:

- GUI не выполняет блокирующий сбор, ожидание диска, остановку трассы и формирование большого отчёта.
- Сборщики, запись и отображение разделены. Для зависающих нативных операций предусмотрены собственные ограниченные по времени механизмы либо изолируемые помощники.
- Очереди, кэши и кольцевые буферы имеют измеряемые пределы. Перегрузка отражается как потеря или неполнота, а не скрывается.
- Важные команды получают подтверждение сохранения. При отсутствии подтверждения интерфейс показывает неопределённый или незавершённый статус.
- Большая история читается страницами; графики используют подготовленные представления. Весь сеанс не загружается в память при каждом перемещении по шкале.
- Экспорт работает потоково и не требует держать полный отчёт в RAM.
- Отмена и остановка имеют определённые переходы состояния и сроки ожидания.
- Сбой одного датчика не уничтожает остальные данные.
- Повторное использование PID, завершение дочернего процесса и отказ доступа учитываются отдельно.
- При нехватке места сохраняется максимально возможная подтверждённая часть записи с честным статусом.
- Восстановление после аварии показывает, какие границы и последние записи могли остаться неподтверждёнными.
- Очистка затрагивает собственные временные материалы. Управление трассами и помощниками ограничено ресурсами, которыми владеет BLACK.BOX.

Для ETW требуется корректно завершать принадлежащие программе сеансы и провайдеры; жизненный цикл трассы является отдельной частью реализации. [S8]

Политики объёма и частоты должны быть понятны пользователю. Произвольный малый предел длительности мешает исследованию; полное отсутствие управления ресурсами может сорвать запись. Нужны настраиваемые бюджеты, предварительная оценка и потоковая работа с большим сеансом.

**14. Интерфейс**

Существующую структуру приложения и локализацию следует сохранить. Детали размещаются внутри текущих экранов, карточек и раскрываемых панелей; новые вкладки не являются целью этого предложения.

В основной работе нужны понятные действия:

- Выбрать программу.
- Проверить готовность наблюдения.
- Начать запись.
- Начать или закончить действие, когда используется ручной замер.
- Отметить проблему.
- Остановить запись.
- Открыть эпизод.
- Сохранить исследование.
- Сравнить повторения.
- Подготовить мою программу.

На общей шкале выделяется интересующий интервал. Выбор эпизода синхронизирует связанные представления. Пользователь видит факты, источники и ограничения; сложные настройки раскрываются по запросу.

Состояния приложения должны различать запись, остановку, сохранение, анализ, неполный результат и ошибку. «Готово» отображается после подтверждённого завершения соответствующей операции.

**15. Работа с чатами и автоматизацией**

BLACK.BOX должен оставаться полезным без встроенной модели и без сетевого аккаунта. Чат получает сохранённый пакет или использует отдельно реализованный интерфейс автоматизации.

Машиночитаемый отчёт содержит стабильные идентификаторы эпизодов, ссылочные доказательства, единицы, качество данных и версии правил. Это уменьшает необходимость вручную пересказывать события между чатами.

Необходимо сохранять границу между измерением и сгенерированным объяснением. Вывод модели хранится как дополнительный анализ с указанием используемых материалов.

Сами журналы исследуемой программы являются недоверенными данными. Инструкции, встреченные внутри них, не должны превращаться в команды помощнику или чату. Автоматические действия задаются через отдельный управляемый интерфейс.

**16. Проверка на собственных тестовых программах**

Нужны воспроизводимые программы с известным поведением и контрольными отметками. Предлагаемые группы:

1. Контролируемая CPU-нагрузка и аналогичный период простоя.
2. Блокировка GUI при работающем фоновом потоке.
3. Поддерживаемая цепочка ожидания и контролируемый цикл ожиданий.
4. Рост памяти с освобождением, удержанием объектов и намеренной утечкой.
5. Ограниченные операции чтения и записи с известным объёмом.
6. Создание и завершение дерева процессов, повторный запуск и проверка идентичности.
7. Доступный и недоступный источник без превращения отказа в нулевое значение.
8. Переполнение очереди или буфера с проверкой учёта пропусков.
9. Замедленный диск, ошибка записи и нехватка места.
10. Сбой датчика или помощника при продолжающейся записи других источников.
11. Инструментированное приложение с известными границами и идентификаторами операций.
12. Полный пользовательский путь в собранном EXE: запись, эпизод, экспорт, открытие на другом ПК, повтор и сравнение.

Проверять нужно и положительные, и отрицательные случаи. Например, BLACK.BOX должен отличать наблюдаемый рост памяти от доказанного удержания объектов, а также от недостаточной информации для такого вывода.

Нагрузочные и длительные испытания из действующего ТЗ сохраняются. Дополнительно проверяются большие истории, расходы RAM при анализе и экспорте, остановка под нагрузкой и сохранность подтверждённых событий.

**17. Критерии законченности**

Готовность продукта определяется сквозными сценариями и обязательствами, а не только успешной сборкой.

Для каждого обязательного требования нужны:

- Реализация в конкретной проверяемой версии.
- Тестовый сценарий и ожидаемое поведение.
- Результат проверки на соответствующей Windows-среде.
- Проверка собранного EXE там, где функция зависит от упаковки и прав.
- Пример артефакта или наблюдения, подтверждающий результат.
- Описание поддерживаемой области и оставшихся ограничений.

Допустимые статусы реализации и проверки: выполнено и проверено; реализовано, проверка не выполнена; частично; отсутствует; неприменимо с установленной причиной.

Для объявленной области выпуска должны проходить: оба режима прав, запись действий, корректность измерений, обработка отказов, сохранение и восстановление, экспорт и повторное открытие, длительная запись и сравнение там, где оно включено в обязательный объём.

Количество зелёных тестов не заменяет проверку пропущенного требования. Статус недоступности источника не заменяет реализацию обязательного адаптера. Неполный патч можно сохранить как рабочий результат; выпуск должен соответствовать заявленному объёму.

**18. Последовательность реализации**

Порядок нужен для промежуточной проверки; обязательства действующего заказа при этом сохраняются.

1. Зафиксировать текущую базу и сопоставить обсуждённые возможности с уже реализованным кодом.
2. Завершить надёжную запись, остановку, сохранение и восстановление; устранить блокирующие ожидания и неверные статусы качества.
3. Довести один полный сценарий исследования действия через собранный EXE.
4. Подключить доступные глубокие Windows-источники с собственными проверками и измерением расходов.
5. Завершить подготовку собственной программы сначала для ограниченного, явно указанного набора сред.
6. Довести переносимый пакет, повторные эксперименты и сопоставление результатов.
7. Провести независимую проверку полноты, длительные испытания и сравнительные пользовательские задачи.

Для доказательства полезности подходят реальные случаи AIO: зависание при сохранении, медленная очередь, рост памяти в длительном сеансе. Сначала требуется независимая контрольная программа с известным поведением, чтобы не принять догадку о сложном приложении за подтверждённую диагностику.

**19. Главная цель выпуска**

Пользователь выбирает программу, воспроизводит проблему, получает проверяемое исследование, передаёт его дальше и может оценить результат исправления. Он понимает происхождение каждого важного утверждения и видит неполноту там, где она возникла.

Именно эту цепочку предлагается сделать отличительной чертой BLACK.BOX. Её ценность должна подтверждаться работающим продуктом и реальными исследованиями.
