# R10 — административная сессия и контракты диагностических операций

R10 — отдельная функциональная разработка поверх Investigation Engine 3 и
существующего Deep Inspection. Версия программы в этой ветке специально не
повышается. Эта документация не означает публикацию или включение R10 в выпуск
v0.5.4. Статус фактической приёмки определяется CI точного коммита Draft PR.

## Административная кнопка

В верхней панели доступно управление административной сессией. Включить её
можно до выбора процесса. После объяснения возможностей и срока пользователь
подтверждает запрос; GUI запускает существующий ограниченный Diagnostic Helper
через штатный Windows `runas` и проверяет его экземпляр и повышенный токен.

GUI остаётся `asInvoker`. Не создаются постоянная служба, механизм хранения
паролей или исполнитель произвольных команд. Начальный предел сессии —
900 секунд. Смена процесса, новые действия и проверки состояния не продлевают
исходный срок.

1. Нажмите «Включить права администратора» и прочитайте объяснение.
2. Подтвердите запрос и, если Windows его показывает, системный UAC.
3. Выберите процесс A. Для нового диагностического контекста отдельно
   подтвердите точный экземпляр процесса и разрешённые операции.
4. Выполните доступные действия. Влияющие на процесс действия требуют своего
   подтверждения цели, параметров и последствий.
5. Выберите процесс Б. Сначала проверяется очистка старого контекста; затем
   отдельно подтверждается новый. Действующий повышенный Helper переиспользуется.
6. Используйте завершение сеанса в верхней панели либо закройте программу.
   Проверьте фактический результат очистки. После истечения срока потребуется
   новая сессия и при необходимости новый UAC.

Перенос административной сессии между целями не переносит согласие на запись
памяти, приостановку потока, отладку или ETW. PID без исходного Windows creation
FILETIME не устанавливает идентичность процесса. Идентичность повторно
проверяется внутри Helper перед выполнением.

## Состояние и очистка

| Состояние | Смысл |
|---|---|
| `INACTIVE` | Действующей административной сессии нет. |
| `REQUESTING_UAC` | Пользователь инициировал запрос прав. |
| `ACTIVE` | Проверены повышенный Helper и действующий срок; нет известной неподтверждённой очистки. |
| `DENIED` | Пользователь или Windows отклонили запрос. |
| `EXPIRED` | Исходный срок истёк. |
| `FAILED` | Запуск, связь или проверка сеанса завершились неудачно. |
| `CLEANUP_REQUIRED` | Очистка старого контекста или результата вмешательства не подтверждена. |

При `CLEANUP_REQUIRED` старый владелец ресурсов сохраняется, а переход к новой
цели не выдаётся за успешный. Используйте штатное завершение/повторную проверку
очистки и изучите результат. Новый `run_id` не доказывает восстановления.
Неизвестное вмешательство не повторяется автоматически.

Отказ UAC не блокирует обычное наблюдение, чтение сохранённых отчётов,
локальную обработку доступных источников и Trace Decoder.

## Добавочные контракты

Существующие `ActionSpec`, `ActionRequest`, `CapabilityManager`,
`InspectorService`, журнал и формат результата сохранены. Новый адаптер v1
добавляет:

- `ToolDescriptor`: существующая операция, входы/выходы, права, последствия,
  бюджеты, владение ресурсами и отмена. Описание не предоставляет прав.
- `RunContext`: конкретный `run_id`, точная цель, параметры, источники,
  подтверждение и общий срок вызова.
- `RunReceipt`: фактический исход вызова, временные границы, атрибуция
  источника/цели, ссылки на результаты, полнота, ограничения и отдельный статус
  подтверждения очистки.

Поля `tool_descriptor`, `run_context` и `run_receipt` дополняют результат
реального `InspectorService.execute`, включая локальные read-only операции и
действия через Helper. Существующие статусы не заменяются новым набором.
`COMPLETED` само по себе не означает подтверждения очистки. Ошибка журнала после
возможного вмешательства сохраняет неопределённость, а не разрешает повтор.

Журнал сохраняет контекст цели у каждой записи. Это позволяет существующему
Investigation Engine 3 читать записи разных процессов без переноса идентичности
с A на Б. JSON/HTML и собственный индекс остаются существующими форматами;
чтение импортированной квитанции не превращает её в аутентифицированный источник.
Байты памяти, секреты и содержимое дампов не добавляются в обычную квитанцию.

## Объём и проверка

R10 не создаёт новый декодер, Evidence Graph, Chain Builder или планировщик
автоматических вмешательств. Используется существующий каталог Deep-действий;
отказы Windows/PPL, отсутствующие данные и неполные источники показываются
по фактическому результату. Неподдержанные параметры не принимаются как
успешно выполненный запрос.

Все тесты приложения и сборки выполняются только стандартными GitHub-hosted
Windows/Linux runners. Сохраняются четыре Windows unit-группы, нативные/Qt/ETW
проверки, Linux и полный portable EXE. Приёмка R10 проверяет реальные два
тестовых процесса, один повышенный Helper, независимое чтение результатов,
отказы, очистку, экспорт/read-back и интерфейс RU/EN при DPI 100–200%.

Интерактивный физический UAC Secure Desktop на обычном hosted runner отдельно
остаётся `NOT_TESTED`. Настоящий токен и native-эффекты не подменяются этой
оговоркой или результатами mocks. Из-за исчерпанного Actions Artifacts storage
доказательства выводятся в журналы/step summaries; новая передача через
`upload-artifact`/`download-artifact` и лишнее кэширование не добавляются.

Исходное техническое задание: [R10](specifications/R10.md). Итоговый русский
технический отчёт содержит точные base/HEAD, PR, выполненные CI jobs, ограничения
и незакрытый шаг после релизной работы R00. Самостоятельный merge и Release
в объём разработки не входят.
