# R50 — ограниченная предыстория и повторяемые исследования

R50 расширяет существующие IncidentCapture, ResearchSession, CaseBook,
статистику действий и Investigation 3. Нового движка доказательств,
автоматического исполнителя вмешательств или Chain Builder здесь нет.
Фактическая приёмка определяется CI точного коммита, а не наличием этой инструкции.

## Пользовательский маршрут

1. В Reports заполните сценарий, версию сценария, нагрузку/входные данные и
   известную версию исследуемой программы. Примените контекст до записи.
2. В настройках профиля выберите Standard, Detailed или Incident Burst и
   нужные триггеры. Настройте время предыстории, лимит измерений и бюджет памяти.
   Применение политики не запускает ETW, дампы или действия Deep.
3. Начните обычное наблюдение своего выбранного процесса. Временные границы,
   точный Windows PID/creation FILETIME и доступный hash файла образа фиксируются
   при начале сеанса. Отсутствие доступа или истечение бюджета оставляет unknown.
4. Для действия используйте существующие Prepare → Begin → End. Границы
   обозначают команды пользователя; внутреннее исполнение приложения они
   автоматически не удостоверяют. Повторите действие при одинаковой нагрузке.
5. Можно вручную отметить проблему. Её происхождение остаётся USER_DECLARED.
   CPU, рост памяти/дескрипторов и I/O используют настоящие наблюдённые счётчики;
   UI-инциденты используют существующие записи Windows responsiveness/WCT.
6. После остановки сравните два сеанса через «Сравнить исследования…».
   Откройте интервалы/инциденты и доступные источники в существующем Investigation 3.
7. «Сохранить сравнение JSON / HTML…» создаёт новый файл с проверкой источников
   и повторным чтением. «Открыть сохранённое сравнение…» читает этот результат.
   Существующие файлы и оригинальные записи не перезаписываются.

## Бюджет и полнота

Предыстория ограничена количеством измерений, временем и учитываемой памятью.
По умолчанию — до 512 измерений и 1 MiB учтённого буфера. Учёт включает
метаданные строк и консервативный запас на Python-объекты; это не квота RSS
всего процесса BLACK.BOX. Actual RSS/CPU и накладные расходы измеряются отдельно.
Отдельной скрытой неограниченной очереди роста памяти нет.

Coverage сохраняет количество фактических и удержанных измерений, вытеснения
по времени/ёмкости/байтам, разрывы последовательности, отсутствующие значения
сенсоров и пропущенные триггеры. Начало записи с короткой предысторией, потеря
измерений и неполная остановка не получают полную coverage. Старый CAPTURED
обозначает завершение операции сбора; отдельная capture_coverage может быть INCOMPLETE.

Исходные sample-данные продолжают храниться существующим recorder. Вытеснение
из ограниченного контекста не удаляет пользовательскую сессию. Для диска и
Incident Burst действуют прежние ограниченные duration/soft-budget/overhead
механизмы ResearchSession; они не объявляются жёсткой файловой квотой.

## Интерпретация триггеров

- Рост памяти — наблюдавшаяся разница, не доказанная утечка.
- I/O burst — наблюдавшийся объём/темп счётчиков, не latency отдельного запроса.
- PROCESS_EXIT_OBSERVED не становится аварией только из-за завершения процесса.
- APP_CRASH_MARKER поступает через существующий cooperative EventTail как
  `process.crash_marker`. Он остаётся APP_SUPPLIED_UNAUTHENTICATED и не доказывает
  аварию средствами Windows.
- CRASH_OBSERVED допускается только для фактически доступной, совпавшей по
  creation FILETIME записи Windows. Поздний Event Log/WER после завершения
  recorder не превращается в выдуманную live-предысторию; используйте R40.

Инцидент сам по себе не доказывает первопричину. Incident Burst не продлевается
бессрочно и не запрашивает UAC/ETW/дамп без соответствующего отдельного действия.

Если в одном измерении одновременно наблюдались несколько включённых сигналов,
первичный триггер сохраняет прежний приоритет, а остальные наблюдённые значения
попадают в secondary signals завершённого инцидента. Однократный скачок RSS или
I/O не должен исчезать из контекста только потому, что одновременно сработал
CPU-триггер. Это контекст одного наблюдения, не дополнительные инциденты и не
доказанная причинная связь между сигналами.

## Сопоставимость

Результат содержит COMPARABLE, NOT_COMPARABLE либо INCONCLUSIVE вместе с
конкретными расхождениями и неизвестными условиями. Проверяются записанные
нагрузка/сценарий/профиль/версия, hash образа, точные идентичности, собственные
временные области, повторения и покрытие нужных для профиля сенсоров.

Разные точные экземпляры одного и того же build могут участвовать в повторении
одной нагрузки. Их PID/FILETIME и события остаются разными; совпавший PID не
объединяет старую трассу с новым процессом. Времена разных запусков не
проецируются на одну шкалу без отдельного доказательства синхронизации.

Метрики показывают доступные внутри действия пары измерений, без экстраполяции
границ и замены missing на ноль. Короткое действие может остаться без пары.
COMPARABLE означает сопоставимые записанные условия; статистическую значимость,
причинность и доказанное «исправлено» результат не утверждает.

Импорт JSON/HTML остаётся UNVERIFIED_IMPORT. Hash обнаруживает изменение
содержимого, но не удостоверяет производителя. Обычный экспорт сравнения
содержит метаданные и ссылки, без байтов памяти и содержимого дампа; применяется
существующая политика редактирования распознаваемых путей и известных закрытых
полей. Универсальное обнаружение секретов в свободном тексте не заявляется.

## Проверка

Все автоматические проверки и сборки выполняются только на стандартных
GitHub-hosted Windows/Linux runners. Контрактные тесты не выдаются за native
Windows-результат. Физические Windows 10/11 и UAC Secure Desktop обозначаются
NOT_TESTED. Из-за изменения маршрута инцидентов и завершения общей волны
требуется отдельная длительная hosted-проверка Standard/Incident Burst по риску.
