# R60 — конструктор диагностических цепочек

R60 добавляет пользовательские графы выполнения внутри **«Обзор → Конструктор цепочек»**. Шесть основных страниц и старый пятистраничный embedding API сохраняются. Это руководство относится к исходному патчу R60; оно не означает публикацию новой версии или завершение его приёмки. Результаты проверки относятся только к указанным в техническом отчёте SHA, workflow и attempt.

Конструктор связывает существующие инструменты BLACK.BOX, сохранённые источники и отдельные решения пользователя. Открытие схемы, профиля или истории не запускает диагностику. `COMPLETED` означает завершение объявленных операций, а не доказанную причину неисправности. Если свидетельств недостаточно, сохраняются `PARTIAL`, `UNKNOWN`, `NOT_ESTABLISHED` либо `RECOVERY_UNCONFIRMED` с исходными ограничениями компонентов.

## Первый запуск цепочки

1. Откройте внутреннюю вкладку конструктора в «Обзоре». Задайте название, базовый профиль и общий бюджет.
2. Выберите инструмент в списке и добавьте узел. Укажите параметры в форме: например, для сохранённой трассы выберите `load_source`, тип `TRACE` и существующий файл.
3. Добавьте `decode_trace`. Соедините выход `source` первого узла со входом `trace` второго. Соединение доступно через порты на полотне и через списки «Из выхода / Во вход»; несовместимый тип отклоняется с причиной.
4. При необходимости добавьте `investigate`, соедините `index → evidence`, затем `export_report`, соедините `case → case` и выберите JSON или HTML. Для анализа допустимых неполных источников явно включите приём частичных входов у соответствующих следующих узлов. Это сохраняет неполноту результата.
5. Нажмите **«Проверить / предпросмотр»**. Просмотрите effective profile, ошибки, требуемые права, эксклюзивные ресурсы и максимальные заявленные бюджеты. Проверка не создаёт успешных диагностических квитанций.
6. Нажмите **«Запустить»**. Живые инструменты используют текущий экземпляр процесса; при несовпадении цели выберите его на странице «Процессы» и явно продолжите. Само подключение не начинает запись.
7. Используйте **«Пауза на безопасной границе»**, **«Продолжить»** или **«Остановить свои операции»**. Пауза прекращает выдачу новых работ и дожидается доступной безопасной границы. Отмена распространяется на операции данного запуска; чужая запись или диагностический контекст не завершаются по совпадению PID.
8. В «Отчётах» откройте историю цепочек, выберите запуск и экспортируйте JSON/HTML. Открытие истории пассивно; продолжение требует отдельного действия.

Сохранение схемы и профиля создаёт новый файл, соответственно `*.bbchain.json` и `*.bbprofile.json`. Существующий пользовательский файл не перезаписывается. Для новой редакции сохраните отдельный файл. Перемещение/удаление узла в редакторе не изменяет результаты уже выполненного запуска.

На полотне доступны перемещение, прокрутка, масштабирование, показ всего графа и управление клавиатурой. Параметры и условия редактируются обычными типизированными формами; ввод произвольного Python, команд или плагинов не поддерживается.

## Подключённые инструменты и порты

Тип порта обозначает семантику источника. SQLite-сеанс OBSERVE не является ETL/EventPipe-трассой и не подключается к декодеру как `TRACE`. Для цепочки «запись ETW → Decoder» нужен отдельный действительный ETW-захват с предусмотренными R10 подтверждениями.

Все инструментальные узлы дополнительно публикуют порт `receipt` типа `RECEIPT` с фактическим `RunReceipt/v1`. Управляющие узлы не выдают себя за диагностические вызовы и не создают фиктивный `RunReceipt`.

| Инструмент | Входы | Выходы | Реальный компонент и граница |
| --- | --- | --- | --- |
| `load_source` | Путь и тип в параметрах | `source`: выбранный тип | Чтение и проверка сохранённого `TRACE`, `TRACE_INDEX`, `SESSION`, `CASE`, `DUMP` или `DEEP_RESULT`; исходник не изменяется |
| `process_select` | PID в параметрах или текущий выбор GUI | `process`: `PROCESS` | Проверяемый Windows PID + creation FILETIME; исторический PID не становится живой целью |
| `observe` | `process`: `PROCESS` | `session`: `SESSION` | Существующий ResearchSession, политика записи, действительное завершение writer/collector |
| `decode_trace` | `trace`: `TRACE` | `index`: `TRACE_INDEX` | Существующий офлайн-декодер ETL/EventPipe/JSONL и его собственная квитанция |
| `load_graph` | `source`: `CASE` | `case`: `CASE` | Повторное чтение сохранённого Evidence Graph |
| `investigate` | `evidence`: несколько `SESSION`, `TRACE_INDEX`, `DUMP`, `DEEP_RESULT`, `INCIDENT` или `EVIDENCE_SET` | `case`: `CASE` | Investigation Engine 3; ссылки без доступного диагностического источника не становятся свидетельствами |
| `critical_path` | `case`: `CASE` или `TRACE_INDEX` | `report`: `REPORT`; `case`: `CASE` | Существующий анализ Critical Path; его `NOT_ESTABLISHED`/`PARTIAL` сохраняются |
| `waits` | `index`: `TRACE_INDEX` | `report`: `REPORT`; `index`: `TRACE_INDEX` | Off-CPU/ReadyThread по доступным событиям планировщика; отсутствие событий не доказывает отсутствие ожиданий |
| `file_io` | `index`: `TRACE_INDEX` | `report`: `REPORT`; `index`: `TRACE_INDEX` | Существующий анализ FileIO с явными фильтрами |
| `disk_io` | `index`: `TRACE_INDEX` | `report`: `REPORT`; `index`: `TRACE_INDEX` | Существующий анализ DiskIO; не подменяет файловую операцию физическим I/O |
| `crash` | `dump`: `DUMP` | `case`: `CASE` | Сохранённый minidump, ограниченный разбор и локальные PE/PDB; дополнительные файлы также проверяются |
| `incident` | `session`: `SESSION`; `incident_id` в параметрах | `incident`: `INCIDENT`; `case`: `CASE` | Действительный сохранённый инцидент, ограниченное окно до/после |
| `compare` | `before`, `after`: `CASE` или `SESSION` | `comparison`: `COMPARISON` | Сравнение совместимых сохранённых исследований/сеансов, без причинного вывода из различий |
| `export_report` | `case`: `CASE`, `COMPARISON` или `REPORT` | `report`: `REPORT` | Существующий экспорт JSON/HTML с проверкой опубликованного результата |
| `session_finalize` | Необязательный набор `after`: `RECEIPT` | `result`: `DEEP_RESULT` | Освобождение ровно того native-контекста, которым владеет текущий запуск; не произвольное завершение R10-сеанса |
| `deep.<operation>` | `process`: `PROCESS`; параметры действующей операции | `result`: `DEEP_RESULT`; у `deep.dump` также `dump`: `DUMP`, у `deep.profile.etw` также `trace`: `TRACE` | Действующий каталог R10, InspectorService и тот же Diagnostic Helper |

Каталог `deep.*` строится из действующего `DEEP_ACTIONS`, включая `processes`, `modules`, `threads`, `handles`, `memory_map`, `memory_read`, `wait_chains`, `network`, `disk`, `snapshot`, `thread_stacks`, `dump`, `profile.etw`, `timeline`, `compare`, `capabilities`, `trace_evidence`, `dump_inspect`, `dump_read_memory`, `symbols_verify`, действия `debug.*`, `thread.suspend`, `thread.resume`, `memory.write`, `memory.rollback`. Наличие названия в каталоге не означает доступность операции для каждой цели: сохраняются её исходные capabilities, права, лимиты и preconditions.

`DEEP_RESULT` без читаемого native-журнала пригоден только для управления по квитанции. Квитанция закрытия контекста также не является диагностическим evidence. Дамп и память не включаются в обычный отчёт автоматически.

## Ветвление и расширение исследования

Граф является DAG: произвольные циклы запрещены. Независимые read-only ветви могут работать параллельно в пределах заданного числа исполнителей и ресурсов. Вмешательства сериализуются; несовместимые владельцы ETW/debugger/записи не обходятся повторным скрытым запуском.

`CONDITION` принимает `input` и сравнивает фактическую квитанцию либо метаданные результата. Доступны сравнения `EQ`, `NE`, `EXISTS`, `GT`, `GE`, `LT`, `LE`, условия статуса, наличия evidence и достаточности, а также ограниченные AND/OR. Типы сравниваются строго: `true` не равно числу `1`. «Достаточно» относится к полноте запрошенной операции и не означает доказанную причину сбоя.

Выбранный выход `true` либо `false` подключается к необязательному управляющему входу `when` следующего узла. При неизвестном результате условия не выбирается ни одна ветвь. Условие `EXISTS` позволяет явно направить поиск на сбор недостающего поля через ветвь `false`. Дополнительные источники и проверки выбирает пользователь; бесконечного автоматического исследования нет.

`JOIN` объединяет входы `evidence`:

- `ALL_REQUIRED`: нужны все требуемые завершённые ветви и независимо проверяемые ссылки;
- `ALLOW_PARTIAL`: пользователь явно допускает неполные ветви. В результате сохраняются частичность и отсутствующие данные; итог не повышается до полного успеха.

Пропущенный обязательный узел не становится успешно выполненным. Для ожидаемо невыбранной ветви можно явно снять обязательность; в истории останутся `SKIPPED`, отсутствие выполнения и квитанции. Source ID, идентичности процессов и clock domains не объединяются в одну доказанную цель/шкалу только из-за наличия ребра.

`REPEAT` допускает только read-only инструмент, конечное число повторов, интервал и бюджет каждого вызова. Каждый фактический вызов получает отдельный идентификатор и результат. Для вмешательств ограниченный повтор также запрещён: отсутствие ответа не даёт разрешения повторить потенциально завершённое действие.

## Профили и бюджеты

Профили `windows`, `application`, `case` используют один движок. Это соответственно явно выбранные области Windows, точный экземпляр приложения и сохранённые доказательства. Профиль Windows не перечисляет все цели и не запускает поиск сам по себе.

Пользовательский профиль может наследовать базовый и задавать overrides допустимых инструментов/узлов, source IDs, целевого ProcessIdentity, времени, числа исполнителей, объёма результатов и планирования вмешательств. Effective profile показывается до запуска; итоговые лимиты пересекаются с лимитами графа. Изменение списка доступных инструментов может сделать сохранённый профиль непригодным, что обнаруживается проверкой.

Source ID сохранённого файла — фактический SHA-256 из выхода `load_source`. Для папки сеанса используется совокупный fingerprint проверенных SQLite-файлов. Ограничение source IDs применяется к выбранным сохранённым байтовым корням и проверенной линии производных файлов. Производный результат сохраняет собственные source ID; они не обязаны совпадать с SHA корня. Дополнительные PE/PDB также должны входить в явно разрешённые SHA. Профиль с ограничением сохранённых корней не разрешает новую живую запись только на основании PROCESS; для неё отдельно выбираются инструменты, цель и свежие подтверждения. Такой ID проверяет неизменность ссылки/байтов и **не удостоверяет происхождение**. Он не заменяет PID + creation FILETIME. Отметка «допустить вмешательства в плане» не является согласием на действие или UAC.

| Ограничение модели | Верхняя граница |
| --- | --- |
| Узлы / связи / глубина DAG | 256 / 1024 / 64 |
| Определение / параметры одного узла | 1 MiB / 16 KiB |
| Read-only исполнители | 4; по умолчанию 2 |
| Общий бюджет | 21 600 секунд; по умолчанию 1 800 |
| Повторы одного узла / фактические вызовы графа | 4 096 / 10 000 |
| Интервал REPEAT | До 3 600 секунд |
| Одновременные объявленные ресурсы | До 64; по умолчанию 8 |
| Результаты запуска | До 4 GiB; по умолчанию 1 GiB |
| Один сохранённый результат / совокупная история метаданных | 512 KiB / 64 MiB |
| SQLite-журнал / события | 128 MiB / 100 000 |

Заявленная последовательная стоимость учитывает каждый повтор и каждый интервал. Предпросмотр не выдаёт её за измеренное время. Более строгие ограничения существующего инструмента продолжают действовать. Deadline и cancellation кооперативны: если native-компонент не подтвердил остановку, живой владелец и неопределённость сохраняются; таймер не считается доказательством освобождения ресурса.

## Подтверждения, checkpoint и восстановление

Перед вмешательством действуют обычные подтверждения R10 с точными целью и параметрами. GUI не повышает собственные права и использует существующий ограниченный Helper. Условия UAC/срока/разрешённого scope не отменяются схемой. Байты `memory.write` запрашиваются заново во время действия и не сохраняются в профиле или графе.

Сервис выдаёт runtime-ссылку владения конкретным native-контекстом. Совпадение PID или scope не позволяет присвоить чужой контекст. Автоматическое завершение и `session_finalize` освобождают только подтверждённого владельца данного запуска и проверяют настоящий cleanup ACK. Известный временно удерживаемый контекст отличается от неизвестной очистки; неудачный `CloseHandle` или незавершённый worker не скрываются состоянием `COMPLETED`.

`CHECKPOINT` останавливает выдачу новых работ, дожидается доступных активных работ и сохраняет `WAITING_FOR_HUMAN`. После явного продолжения повторно проверяются хеши файлов, доступность источников и применимые живые идентичности. Старое согласие не восстанавливается с диска. Изменившийся источник или экземпляр процесса блокирует продолжение; завершённые результаты сохраняются со своей исходной идентичностью.

Если процесс BLACK.BOX/Helper прервался между durable intent и результатом, незавершённый вызов не превращается в успех. Неопределённое вмешательство не повторяется автоматически. Прежний runtime native-контекст нельзя восстановить из сохранённого `confirmed` или из номера PID. При `RECOVERY_UNCONFIRMED` изучите точную причину, фактическую очистку и исходный журнал; новый независимый запуск требует нового решения пользователя.

## История, экспорт и устройство исходников

Определение схемы, история конкретного запуска и диагностические источники разделены. В папке запуска находятся неизменяемое `definition.bbchain.json`, `workflow-run.json`, действующий EvidenceJournal (`journal/deep-inspection.sqlite3`), private `.results/<node_run_id>.json` и результаты операций. Sidecar хранит ограниченные ссылки и метаданные, а журнал связывает его с конкретным запуском через hash, размер, файловую идентичность и ID. Это нужно для сохранения fingerprint без потери полей при штатной редакции чувствительных payload журнала.

Открытие проверяет SQLite integrity, hashchain, схемы и семантические связи sidecar. Один writer имеет проверяемое владение историей. Повреждённая или отсутствующая запись не заменяется новым пустым журналом. Локальная hashchain обнаруживает изменения, но не является криптографической аутентификацией внешнего производителя.

Экспорт истории использует существующую транзакцию публикации: новый файл, ограниченный размер, независимое повторное чтение JSON либо встроенного JSON в HTML и проверка опубликованных байтов. В отчёте сохраняются исходные статусы, RunContext/RunReceipt, upstream/downstream IDs, источники и cleanup; пути, сырая память/дампы, payload и runtime-полномочия исключаются согласно существующей политике публичных метаданных. Политика распознаёт известные чувствительные поля, пути и URL; она не обещает обнаружить произвольный секрет в свободном тексте.

| Модуль | Ответственность |
| --- | --- |
| `chain_contracts.py`, `chain_validation.py` | Версионированная модель, типы, DAG, условия и пассивная проверка |
| `chain_profiles.py`, `chain_io.py` | Профили, ограничения, fingerprint и повторная проверка источников |
| `chain_engine.py` | Ограниченные исполнители вне Qt GUI, очередь, зависимости, leases, pause/cancel/recovery |
| `chain_adapters.py` | Вызов реальных существующих компонентов и сохранение их квитанций |
| `chain_store.py`, `chain_reports.py` | Проверяемая локальная история и экспорт с readback |
| `blackbox_universal/chain_builder.py`, `chain_bridge.py` | Редактор/история и связь с существующими GUI-владельцами |
| `chain_qa.py`, `chain_qa_native.py`, `tools/qa_chain_builder.py`, `qa_chain_endurance.py` | Отдельные явные QA-входы и независимые проверки |

## Границы проверки

Статическая доступность узла, успешная unit-fixture и реальная Windows-операция — разные свидетельства. Windows PID/creation FILETIME и native Helper не эмулируются на Linux. Недоступные права, неподключённый источник, неизвестная версия, отсутствие событий или символов показываются явно.

Изолированный `bb-r60-qa.yml` проверяет contracts на Windows/Linux и отдельный действительный source/frozen Windows E2E, Standard token, исходные R10-регрессии, RU/EN и DPI через Qt scale 100–200%. Полная кандидатская приёмка также требует действительный 5ч30 lifecycle и все прежние обязательные gates, включая часовые Standard/Incident Burst и portable maintenance. Успех отдельных development jobs не равен полной приёмке.

Hosted Windows и Qt scale не доказывают физическую приёмку Windows 10/11 или Secure Desktop. Они остаются отдельными испытаниями. Конструктор не добавляет WPP/TMF, универсальный анализ heap, внешние AI-сервисы или автоматическое удостоверение импортированных трасс. Публикация Release и перенос R60 в MAIN требуют отдельных предусмотренных решений владельца; это руководство таких решений не подменяет.
