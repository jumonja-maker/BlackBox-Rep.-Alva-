# BLACK.BOX Trace Decoder — этап 3 / Phase 3: provenance временных меток

**Режим:** только разработка в `main`, без GitHub Release и без изменений
алгоритмов записи/наблюдения. Этот этап вводит достоверное отображение того,
*что TraceEvent сообщил о часах трассы*; не объявляет, что часы уже синхронизированы
с Windows-сеансом BLACK.BOX.

## Реализовано

- В изолированном Microsoft TraceEvent helper при декодировании настоящих
  `.etl` и `.nettrace` помимо уже записанных `time_ms` (относительная шкала
  трассы) и `source_ticks` сохраняется `utc_ticks` — календарное время,
  **восстановленное самим TraceEvent из счётчика трассы**.
- Новый индекс `blackbox.decoder-index/3` хранит `utc_time_ns` как знаковое
  SQLite INTEGER, а также точную строку `utc_time_iso` и пометку
  `TRACEEVENT_DERIVED_UTC_UNVERIFIED`. Точность хранения 100 нс — **не**
  утверждение точности измерения часов или отсутствия дрейфа.
- Шестая вкладка: режим **Trace UTC estimates / Оценки времени UTC**,
  буквальный поиск по провайдеру/событию, фильтр PID, постраничный просмотр
  событий в том же порядке, что в исходной трассе. Каждая запись показывает
  исходные QPC ticks и UTC в подробностях.
- `TraceClockAudit` сравнивает изменения UTC-проекции с относительным временем
  трассы. Расхождение более 10 мс отмечается как
  `TRACE_RELATIVE_VS_UTC_DISAGREEMENT_UNCERTAIN`; не обнуляется и не
  исправляется подстановкой другой временной шкалы. Для 0 записанных
  UTC-событий статус `TRACE_UTC_NOT_RECORDED`; для частичной трассы —
  `PARTIAL_TRACE_UTC_PROJECTION`. Некорректные десятичные ticks и диапазон
  вне вместимости SQLite отклоняются, частичный индекс не публикуется.
- Собственные `BLACK.BOX JSONL`, у которых нет подтверждённого источника UTC,
  **не получают выдуманных UTC timestamps**. Просмотр этого режима остаётся
  пустым с явной информацией о недоступных календарных метках.
- Сохранённые индексы v1/v2 читаются в прежних режимах. Для UTC-режима
  необходимо повторно декодировать оригинальную трассу в v3. Исходные
  файлы не мигрируются и не изменяются.

## Важнейшее ограничение: это ещё НЕ синхронизация

TraceEvent `TimeStamp` получается из временных данных TraceLog; это
календарная проекция, а не независимая UTC-аттестация и не доказательство
идентичного QPC origin с Python `time.monotonic_ns`.
Импорт мог быть сделан на другом компьютере или после перезагрузки;
системные часы могли измениться, а журнал мог потерять события.
Поэтому индекс всегда сообщает:

- `trace_to_blackbox_session_clock_alignment: NOT_ESTABLISHED`;
- `same_boot_same_machine_and_time_sync: NOT_VERIFIED`;
- `capture_complete: null`, а не `true`;
- `verification_class: UNVERIFIED_IMPORT`.

**Нельзя** автоматически связывать GC-паузу с GUI-зависанием, потоком
пользовательского сеанса или чужим PID на основании совпавшего UTC.
Несопоставимые часы не превращаются в правдоподобное единое время.

Для доказуемой синхронизации необходим **следующий отдельный этап**:
сбор пар QPC/monotonic/UTC с погрешностями *во время самой записи*,
подтверждение владения трассой и её SHA-256, проверка той же ОС/загрузки
и поколения PID, контроль дрейфа на интервале и явная политика отказа
при потерях. Этот Phase 3 не добавляет эти датчики автоматически,
не изменяет пользовательские профили и не увеличивает нагрузку
на наблюдаемое приложение.

## QA / Verification

- Синтетические тесты проверяют UTC ticks, исходные source ticks,
  возрастающие и неупорядоченные события, keyset-пагинацию, поиск/PID,
  неверные Unicode-цифры, выход за диапазон и окно дрейфа >10 мс,
  в том числе отсутствие публикации частичного индекса.
- Тесты Qt (EN/RU) проверяют новый режим, подписи UTC и реальный выбор
  строки с `TRACEEVENT_DERIVED_UTC_UNVERIFIED`.
- `tools/qa_decoder.py` декодирует **реальную EventPipe** тестового
  .NET-приложения, проверяет UTC и QPC одновременно с GC и выборками
  стека; на Windows также разбирает настоящий ETL-провайдер.
- GitHub CI — это тестовый runner, не аттестация часов или проверка
  физической Windows 10/11 в лаборатории.
