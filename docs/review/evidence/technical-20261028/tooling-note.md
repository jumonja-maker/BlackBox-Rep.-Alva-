## Подтверждено и исправлено

### BB-10 / P3 — владелец POSIX-группы терял потомка после нормального выхода лидера

`OwnedProcess.close(kill=False)` проверял только непосредственный Popen. Когда он уже завершился, cleanup не посылал сигнал собственной группе, но ставил `_closed=True`. Следующий `close(kill=True)` уже ничего не делал.

Первый close теперь завершает собственную POSIX-группу независимо от состояния её лидера и только затем освобождает capability. Popen по-прежнему создаётся с `start_new_session=True`; чужие процессы по имени/PID-списку не завершаются. Идемпотентность после успешного close сохранена. Windows Job Object путь не заменён POSIX-сигналами.

**Отрицательное воспроизведение:** в отдельном Linux subprocess активирован subreaper; собственный родитель запускает собственного ребёнка с heartbeat и нормально выходит. До исправления heartbeat продолжался и после обычного, и после принудительного close. После исправления прекращается. Отдельная контрольная группа остаётся живой. Fixture завершает и reap-ит собственных детей. Для проверки жизни используются реальные изменения heartbeat, а не `/proc`: в облачной среде PID namespace процессов не совпадает с видимой procfs. Первая проба с `/proc` была отброшена как недостоверная и не используется как доказательство.

Это контроль Linux process-group cleanup, не Windows-нативная проверка. Потенциальные процессы, специально создавшие другую сессию, и произвольные чужие daemon-деревья этой границей не охватываются.

### Дополнительный P2 — потеря процесса при отказе ready marker после успешного Popen

`OptionalJobs._launch` после создания owner записывает `ready`. Если это действие отказывает (например, диск/доступ), прежний except очищал только временную папку; owner терялся, а процесс продолжал работу. Реальный OwnedProcess с инъекцией `Path.touch` отказа остался работающим до исправления. Новый except сначала запускает bounded owner cleanup, затем temp cleanup и заново выбрасывает первоначальную ошибку.

Вторая ошибка cleanup раньше подменяла первоначальный диагноз. Теперь исходная ошибка сохраняется, а вторичная добавляется как exception note. Отдельная регрессия одновременно отказывает запись marker и cleanup temp; сохранён исходный текст ошибки, созданный процесс остановлен. Это не обещание удаления файла при физически запрещённом ОС cleanup: проверяется корректная попытка и сохранение исходного отказа.

## Undefined-name gate

`tools/check_undefined_names.py` использует Pyflakes как **QA-only** зависимость, не импортируется приложением и не меняет runtime dependencies. Проверяются `UndefinedName`, `UndefinedLocal`, `UndefinedExport`, некорректные forward annotations, синтаксические ошибки и ошибки чтения. Неиспользованные импорты/переменные не блокируют этот узкий gate. При отсутствии инструмента или входного пути — `INCOMPLETE`, exit 2; проблемы binding/syntax — `FAIL`, exit 1; чистый анализ — `PASS`, exit 0.

По умолчанию: `src`, `blackbox_universal`, `tools`, `tests`, `app.py`, `maintenance_entry.py`. На текущем дереве: **226 Python-файлов PASS**, ни одной finding. Число файлов увеличится после остальных направлений патча — окончательная проверка root авторитетна. Pyflakes надо устанавливать из закреплённых QA requirements во всех workflows, запускающих полный новый suite; это не зависимость поставляемого EXE.

Команда:

```bash
PYTHONPATH=src:. ../bb-venv/bin/python tools/check_undefined_names.py --report ../blackbox-audit-20261028-state/undefined-names.json
```
