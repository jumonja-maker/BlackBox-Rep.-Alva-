# BLACK.BOX — Техническое задание BB-INV-003

## Investigation Engine 3 — Evidence Graph & Guided Diagnostics

**Проект:** BLACK.BOX Universal\
**Тип разработки:** крупный функциональный патч\
**Базовая версия:** v0.5.3\
**Базовый commit:** `dafa9cdb4b0f4766fc8cd2d5fd0d43579459e485`\
**Предлагаемая следующая версия:** v0.5.4\
**Платформа:** Windows 10/11 x64\
**Интерфейс:** существующий Overview и Deep Inspection\
**Режим разработки:** отдельная ветка, полный патч, GitHub-hosted CI, PR и независимая приёмка

## 1. Главная цель

Создать систему, которая не просто собирает диагностические данные, а связывает их между собой, выявляет наблюдаемые зависимости, формирует проверяемые гипотезы и предоставляет пользователю последовательный путь расследования.

Сейчас BLACK.BOX умеет получать:

- CPU, RAM, I/O и историю процессов.
- Модули, дескрипторы, память и стеки потоков.
- Данные ETW, EventPipe и WCT.
- События планировщика Windows.
- Дамп процесса и отладочные контексты.
- Сведения о пользовательских действиях и инцидентах.
- Результаты диагностического вмешательства.
- Снимки ДО/ПОСЛЕ.
- Исторические трассы и локальные символы.

Однако большая часть этих возможностей анализируется раздельно.

**Задача BB-INV-003 — объединить их в одну систему расследования с доказуемыми связями между наблюдениями.**

Программа должна уметь отвечать на четыре практических вопроса:

1. Что именно происходило с исследуемым приложением?
2. Какие потоки, операции, модули и события связаны с обнаруженной проблемой?
3. Какие объяснения подтверждаются данными, а какие остаются предположениями?
4. Что пользователь может сделать для проверки предполагаемой причины?

BLACK.BOX не должен придумывать отсутствующие доказательства или выдавать совпадение по времени за установленную причинно-следственную связь.

## 2. Основной принцип архитектуры

**Нельзя строить второй независимый диагностический движок с дублированием уже имеющихся функций.**

В существующем проекте необходимо переиспользовать:

`BLACKBOX_INVESTIGATION_2` и старые результаты должны продолжить открываться.

## 3. Evidence Graph — граф доказательств

Это центральный компонент патча.

### 3.1. Назначение

Разработать движок, создающий граф связей между диагностическими событиями.

Граф должен поддерживать следующие типы объектов:

- Экземпляр процесса.
- Экземпляр потока.
- Модуль и функция.
- Снимок стека.
- Событие CPU.
- Интервал ожидания.
- Файловая или сетевая операция.
- Событие планировщика.
- Обнаруженная ошибка или инцидент.
- Действие пользователя.
- Диагностическое вмешательство.
- Результат измерения.
- Сохранённый дамп или трасса.

**Пример исследовательской цепочки:**

`Инцидент → Поток → Интервал ожидания → Связанное событие → Стек → Модуль → Функция`

Такая последовательность должна строиться только при наличии подтверждённых связей. Если связь отсутствует, граф должен явно показывать разрыв.

### 3.2. Степени достоверности связи

Разработать типизированные связи:

| Класс | Значение |
|---|---|
| `EXACT_IDENTITY` | Совпадение проверенной идентичности объекта |
| `DIRECT_REFERENCE` | Прямая ссылка из исходного события |
| `BOUNDED_TIME_CORRELATION` | Временная связь с установленными границами погрешности |
| `OBSERVED_DEPENDENCY` | Наблюдаемая связь ожидания или выполнения, поддержанная источником |
| `TEMPORAL_COINCIDENCE` | Совпадение по времени без доказательства зависимости |
| `HYPOTHESIS_ONLY` | Предположение, требующее проверки |
| `NOT_ESTABLISHED` | Связь установить не удалось |
| `CONTRADICTED` | Связь противоречит подтверждённым данным |

Не использовать искусственный процент уверенности без модели, прошедшей независимую проверку и калибровку.

Отображаемый граф должен различать наблюдаемые факты, результаты вычисления и предположения.

### 3.3. Идентичность процессов и потоков

Для живого процесса использовать как минимум PID и точный Windows creation FILETIME, с проверкой образа там, где это возможно.

Для потоков использовать TID и время создания.

Идентификаторы `ProcessIndex` и `ThreadIndex` из TraceEvent считать идентификаторами конкретной трассы.

Запрещается автоматически связывать исторические события с живым процессом только по PID, TID, имени или приблизительному UTC.

Если подтверждение отсутствует, связь должна оставаться `NOT_ESTABLISHED`.

### 3.4. Временная корреляция

Обязательно переиспользовать `decoder_alignment.py` и существующие проверки часов.

Новый движок не должен самостоятельно вычислять «точное совпадение» часов из приблизительных меток.

Необходимо:

- Сохранять исходную временную шкалу каждого источника.
- Проверять допустимость преобразования часов.
- Учитывать границы неопределённости.
- Отвергать неподтверждённую связь разных загрузок Windows или разных экземпляров процесса.
- Сохранять сведения о потерях, неполноте и перестановках событий.

Для неподтверждённой временной связи можно показывать отдельные группы событий, но нельзя изображать их как единую доказанную последовательность.

## 4. Анализ критического пути выполнения

Разработать модуль **Critical Path Analyzer**.

### 4.1. Основные задачи

На основе имеющихся ETW, WCT и CPU-данных определять:

- Какие потоки исполнялись.
- Какие потоки ожидали.
- Когда поток был готов к выполнению, но не получал процессор.
- Какие события пробуждали поток.
- Какие наблюдаемые операции предшествовали задержке.
- Какие участки выполнения потенциально ограничивали завершение операции.

### 4.2. Модель времени

Отдельно представлять:

- `RUNNING` — наблюдаемое выполнение.
- `BLOCKED` — ожидание.
- `READY` — готовность к выполнению.
- `UNKNOWN` — состояние нельзя установить.
- `INCOMPLETE` — интервал ограничен потерянными или неполными событиями.

Использовать уже реализованную логику `decoder_waits.py`.

Не заменять недостающие события интерполяцией, которая создаёт ложные зависимости.

### 4.3. Граф зависимостей

Построить ориентированные связи между наблюдаемыми интервалами и событиями.

Критический путь можно вычислять только для согласованного подграфа с подходящими временными границами и подтверждёнными зависимостями.

При недостаточных данных отображать частичный путь и неизвестные участки.

**Особое правило:** событие ReadyThread или признак пробуждающего потока не являются сами по себе доказательством владельца конкретной блокировки.

Сведения WCT использовать там, где они непосредственно поддерживают соответствующую связь. Не переносить такую связь на другой момент времени без подтверждения.

### 4.4. Результат

Пользователь должен видеть временную диаграмму потоков, подсвеченные участки задержки, связанные стеки и список неопределённых зависимостей.

Пример корректного вывода:

«Поток находился вне CPU 1840 мс. Из них 1320 мс подтверждены как ожидание, 520 мс — как задержка готового потока. Причина ожидания по доступным событиям не установлена».

Числа в реальном отчёте должны вычисляться только из записанных данных; пример выше не является ожидаемым результатом теста.

## 5. Operation Correlation — связь операций с ошибками

### 5.1. Назначение

Создать единый интерфейс исследования файловой, сетевой и иной доступной системной активности.

Для операции, если источник действительно предоставляет сведения, показывать:

- Тип операции.
- Процесс и поток.
- Объект или ресурс.
- Время начала и завершения либо доказанный интервал.
- Размер передачи.
- Результат выполнения.
- Код ошибки.
- Стек или модуль.
- Связанные события.

### 5.2. Файловые операции

Переиспользовать ETW FileIO и существующий декодер.

Поддержать сопоставление операций с уже записанными пользовательскими событиями `io.operation.end`, где имеются соответствующие идентификаторы и поля.

Если источник предоставляет только факт операции, запрещено выдумывать `SUCCESS`, `ACCESS_DENIED`, задержку или стек.

При наличии подходящего идентификатора операции, объекта или связанного события показывать установленную связь; простое временное соседство отмечать отдельно.

### 5.3. Реестр Windows

Спроектировать типизированный интерфейс источника для будущего сбора операций реестра.

При этом **не объявлять трассировку реестра реализованной**, пока не появятся настоящий Windows collector, парсер, проверки прав и нативные испытания.

В текущий обязательный объём BB-INV-003 входит корректное представление уже существующих допустимых источников. Полноценный захват реестра уровня Process Monitor относится к отдельному расширению.

### 5.4. Сеть и диск

Использовать доступные TCP/UDP, FileIO и DiskIO.

Строго разделять сетевые метаданные, объёмы событий, процессные I/O-счётчики и физические DiskIO completion.

Не вычислять задержку конкретного файла из несвязанных системных дисковых событий.

## 6. Hypothesis Engine — система диагностических гипотез

### 6.1. Цель

После построения графа движок должен предлагать возможные объяснения обнаруженной проблемы, а не просто выдавать набор измерений.

Поддержать категории:

- Высокая загрузка CPU.
- Задержка выполнения.
- Ожидание и вероятная взаимоблокировка.
- Рост памяти.
- Ошибки файловых операций.
- Проблемы сети.
- Неожиданное завершение процесса.
- Неотзывчивость пользовательского интерфейса.
- Неудачное диагностическое действие.

### 6.2. Структура гипотезы

Каждая гипотеза должна иметь:

- Уникальный идентификатор.
- Понятное описание.
- Ссылки на подтверждающие факты.
- Противоречащие факты.
- Альтернативные объяснения.
- Недостающие данные.
- Предлагаемый способ проверки.
- Статус проверки.

Статусы:

`CANDIDATE`, `SUPPORTED_BY_OBSERVATION`, `SUPPORTED_BY_CONTROLLED_EXPERIMENT`, `CONTRADICTED`, `INCONCLUSIVE`, `USER_CONFIRMED`.

`USER_CONFIRMED` означает вывод пользователя, а не автоматическое доказательство движка.

### 6.3. Запрет ложных выводов

Запрещается выводить установленную первопричину только из:

- Высокого CPU.
- Роста RSS или Private Bytes.
- Совпадения двух событий по времени.
- Наличия стека функции.
- Причины ожидания Windows.
- Успешной записи или восстановления байтов памяти.
- Уменьшения задержки после вмешательства без дополнительных контролей.

Отчёт должен указывать конкретное основание каждого вывода.

### 6.4. Предложение следующего действия

Реализовать **Next Diagnostic Action Advisor**.

Примеры:

- Неизвестен выполняющийся код → предложить собрать CPU-стек.
- Неизвестно, почему поток ожидает → предложить WCT или ETW.
- Подозрение на повреждение состояния → предложить дамп или контролируемое чтение памяти.
- Не хватает сравнений → предложить повторить тот же сценарий.
- Недостаточно прав → предложить UAC для конкретной операции.

Предложения должны формироваться на основе реально доступных действий и их контрактов.

Не предлагать недоступную функцию как существующую.

## 7. Управляемая проверка гипотез

Это связующее звено между новым движком и BB-DEEP-001.

Пользователь выбирает гипотезу и запускает диагностический эксперимент.

### 7.1. Последовательность

1. Выбрать гипотезу.
2. Показать подтверждающие данные и ограничения.
3. Определить, какие измерения необходимы.
4. Сохранить состояние ДО.
5. Предложить требуемое диагностическое действие.
6. Получить согласие и необходимые разрешения.
7. Выполнить действие через существующий Diagnostic Action Engine.
8. Сохранить результат.
9. Повторно измерить состояние.
10. Сравнить ДО/ПОСЛЕ и оценить гипотезу.

Все шаги вмешательства должны использовать существующий `InspectorService`, `ActionRequest`, capability checks и журнал.

### 7.2. Запрос административных прав

**Программа должна самостоятельно предлагать пользователю системный UAC, когда выбранное действие требует администратора.**

Нельзя возвращаться к подходу, при котором функция просто сообщает «запустите программу от имени администратора», хотя повышение можно запросить поддерживаемым механизмом Windows.

Основной GUI остаётся `asInvoker`.

Повышается только отдельный ограниченный Diagnostic Helper. Подтверждение связано с конкретным экземпляром процесса и разрешёнными действиями.

Отказ пользователя от UAC не должен ломать исследование.

### 7.3. Безопасность воздействия

Сохранить механизмы BB-DEEP-001:

- Явное подтверждение.
- Временные ограничения.
- Контроль собственного изменения состояния.
- Сравнение предыдущего и нового состояния.
- Попытка восстановления с проверкой.
- `RECOVERY_UNCONFIRMED` при неопределённом результате.

Нельзя автоматически повторять вмешательство после потери подтверждения его результата.

**Главное:** пользователь получает реальные инструменты исследования и вмешательства, а не лишние искусственные запреты. Одновременно он должен видеть последствия каждого действия.

## 8. Issue Grouping — повторяющиеся проблемы

Реализовать локальный механизм группировки похожих инцидентов по разным сеансам.

### 8.1. Отпечаток проблемы

Строить устойчивый fingerprint с использованием доступных подтверждённых характеристик:

- Тип инцидента или ошибки.
- Проверенный код ошибки.
- Вид операции.
- Нормализованные адреса модуля и RVA.
- Проверенную идентичность модуля.
- Записанный стек.
- Идентичность исследуемого приложения.
- Контекст сценария, если пользователь его указал.

Не использовать случайный PID, абсолютный ASLR-адрес, путь пользователя или одну только текстовую формулировку ошибки как достаточный ключ объединения.

Если сильного отпечатка нет, результат остаётся кандидатом на группировку.

### 8.2. История проблемы

Показывать:

- Первое наблюдение.
- Повторные появления.
- Связанные сеансы.
- Версии исследуемого приложения.
- Изменение наблюдаемой частоты.
- Пользовательские пометки.
- Доказательства возможного исправления и повторного возникновения.

### 8.3. Регрессии

Если один и тот же сценарий выполнен на разных версиях приложения, сравнить результаты.

Обязательные условия сравнения:

- Совместимый сценарий.
- Сопоставимая нагрузка.
- Достаточное покрытие измерениями.
- Сопоставимые источники.
- Корректная идентичность каждого сеанса.

Если условия не выполнены, выводить `NOT_COMPARABLE`.

Отсутствие ошибки в неполном сеансе не доказывает её исправление.

### 8.4. Управление группами

Предусмотреть ручное объединение и разделение групп с сохранением причин изменения.

Не изменять исходные события и не удалять их при перегруппировке.

Никакой облачной синхронизации и регистрации пользователя.

## 9. Интерфейс программы

**Не создавать новую основную вкладку.**

BLACK.BOX сохраняет шесть существующих страниц.

Главная точка входа — **Overview**, внутри существующего Deep Inspection.

### 9.1. Вход в расследование

Добавить действие:

**ИССЛЕДОВАТЬ ПРОБЛЕМУ / INVESTIGATE PROBLEM**

После выбора процесса или сохранённого инцидента открывается раскрываемая рабочая область внутри Overview.

В рабочей области должны быть следующие внутренние разделы:

| Раздел | Назначение |
|---|---|
| Обзор проблемы | Что обнаружено, время, объект и степень полноты |
| Связанные события | Единая шкала наблюдаемых фактов |
| Граф доказательств | Связи между процессами, потоками, стеками и операциями |
| Критический путь | Выполнение, ожидания, готовность и неизвестные участки |
| Гипотезы | Возможные объяснения и противоречащие факты |
| Проверка | Снимки ДО/ПОСЛЕ и доступные диагностические действия |
| Повторения | Связанные инциденты, версии и результаты сравнений |

Это внутренние разделы инструмента, а не новые пункты главной навигации.

### 9.2. Поведение интерфейса

Интерфейс должен показывать сначала краткую информацию, затем позволять углубиться.

Пользователю должны быть доступны:

- Переход от события к конкретному потоку.
- Переход от стека к модулю и поддерживаемому символу.
- Открытие выбранного интервала в Trace Decoder.
- Возврат к исходному инциденту.
- Просмотр всех источников конкретного утверждения.
- Сравнение нескольких наблюдений.
- Запрос дополнительных измерений.

Если данные отсутствуют, показывать не просто «Недоступно», а конкретное объяснение и допустимое следующее действие.

### 9.3. Требования UX

- RU/EN.
- DPI 100/125/150/200%.
- Отсутствие блокировки Qt event loop.
- Асинхронные операции с отменой.
- Виртуализация больших списков и ограниченная визуализация графа.
- Клавиатурное управление и читаемые состояния.
- Сохранение выбора расследования при переходах внутри интерфейса.
- Запрет применения старых результатов к новому выбранному процессу.

Открытие Overview не должно автоматически запускать трассировку, отладчик, дамп или запрос UAC.

Не проводить разрушительные миграции старых сеансов.

При повторном построении индекса результат должен быть воспроизводимым для одинаковых входных данных, версии алгоритма и параметров.

Повреждённый, изменившийся или неподдерживаемый источник должен давать явное состояние, а не частично опубликованный результат, похожий на успешный.

Каждая операция должна поддерживать ограничение времени, памяти, объёма результата и отмену.

## 11. Производительность и ограничения ресурсов

Обработка должна быть локальной, ограниченной и пригодной для больших трасс.

Для первого релиза установить проверяемые бюджеты:

- Не более 250 000 событий на один выбранный проход без постраничного продолжения.
- Не более 10 000 узлов и 20 000 связей в одном отображаемом графе.
- Постраничная загрузка событий и связанных проблем.
- Отсутствие обязательной загрузки всей трассы в оперативную память.
- Возможность отмены долгого анализа.
- Атомарная публикация готового результата.
- Сохранение информации о пропущенных данных при достижении лимита.

Ограничение визуализации не должно означать молчаливую потерю сохранённых исходных данных.

Для крупных источников предусмотреть последовательную обработку выбранных временных интервалов.

## 12. Защита данных и безопасность

Программа остаётся local-first.

Не добавлять обязательную регистрацию, облачные API, скрытую телеметрию или автоматическую передачу диагностических данных.

В обычный экспорт не включать содержимое памяти, полные дампы, секреты из окружения, пароли, токены и чувствительные значения из реестра.

Для импорта файлов обязательны:

- Ограничение размеров.
- Проверка схем.
- Проверка целостности.
- Отказ от выполнения импортированного кода.
- Безопасное отображение пользовательских строк.
- Защита от повреждённых SQLite/JSON/ETL и некорректных временных меток.

Модуль построения графа не должен получать административные права только для чтения уже сохранённых данных.

Все реальные вмешательства выполняются через существующую подсистему BB-DEEP-001.

## 13. Подготовка к пользовательским цепочкам автоматизации

Новый движок должен быть совместим с будущим конструктором диагностических сценариев.

Он должен уметь предоставлять структурированную последовательность потенциальных шагов:

`Обнаружение → Сбор доказательств → Корреляция → Гипотеза → Подтверждение действия → Проверка → Отчёт`

Но **выполнение этой последовательности не должно навязываться пользователю**.

Для каждого шага описать входные данные, выход, права, влияние, лимит времени, условия продолжения, отмену и очистку.

Реализовать программный интерфейс подготовки сценариев и ручного последовательного выполнения.

Полноценный визуальный редактор произвольных цепочек является отдельным следующим этапом разработки.

Пользователь должен сохранять контроль над диагностическими действиями.

## 14. Обязательные сценарии испытаний

### Сценарий A — зависание потока

Контролируемое приложение создаёт поток, ожидающий объект синхронизации.

BLACK.BOX должен:

1. Обнаружить доступный интервал ожидания.
2. Найти соответствующие ETW/WCT-сведения.
3. Построить подтверждённые связи.
4. Отдельно показать неподтверждённые зависимости.
5. Предложить подходящее дополнительное исследование.

Не объявлять причину блокировки доказанной без соответствующего источника.

### Сценарий B — файловая ошибка

Контролируемое приложение выполняет файловую операцию с ожидаемым отказом.

Должны быть отдельно проверены исходные события приложения, доступные ETW-метаданные, соответствие идентификаторов и формирование гипотезы.

Если ETW не содержит код ошибки, движок не должен переносить его из неподтверждённого совпадения.

### Сценарий C — высокая загрузка CPU

Создать известную вычислительную нагрузку.

Получить настоящие CPU-сэмплы и доступные стеки.

Показать горячие участки и источник наблюдений. Не заменять количество сэмплов процентом CPU или временем исполнения функции.

### Сценарий D — повторяющаяся ошибка

Создать несколько сеансов с одинаковой ошибкой и отдельный сеанс с похожей, но иной ошибкой.

Проверить правильную группировку и отсутствие ложного объединения.

Добавить сравнение версий с сопоставимой нагрузкой.

### Сценарий E — диагностическое вмешательство

Создать снимок ДО, изменить контролируемое состояние процесса через Diagnostic Helper, затем снять ПОСЛЕ.

Проверить журнал, точную идентичность цели и корректность сравнения.

Система не должна утверждать, что вся обнаруженная разница обязательно вызвана вмешательством.

### Сценарий F — недостоверная трасса

Подать данные с:

- Повторно использованными PID/TID.
- Несовпадающей идентичностью источника.
- Различными временными шкалами без доказанной корреляции.
- Потерянными или переставленными событиями.
- Неполными стеками.
- Неизвестными полями.
- Повреждённым файлом.

Проверить отсутствие ложных доказательств, зависания и неконтролируемого потребления ресурсов.

### Сценарий G — недостаточные разрешения

Выбрать действие, которому необходимы административные права.

BLACK.BOX должен показать требование, предоставить возможность запроса UAC через существующий helper и корректно обработать отказ.

Интерактивный Secure Desktop не объявлять проверенным на GitHub runner, который его не предоставляет.

### Сценарий H — реальный пользовательский маршрут

На GitHub-hosted Windows проверить весь маршрут:

**Overview → Инцидент → Граф → Поток → Стек → Гипотеза → Выбор действия → Проверка ДО/ПОСЛЕ → Экспорт.**

Использовать настоящий Qt, настоящие контролируемые процессы и реальные диагностические источники там, где сценарий заявлен нативным.

Тест должен проверять результат и содержимое доказательств, а не только факт вызова метода.

## 15. GitHub CI и проверка качества

Все автоматизированные тесты проводить **исключительно на GitHub-hosted runners**.

Обязательные gates:

1. Контракты схем и корреляции на Windows/Linux.
2. Настоящие Windows-процессы, потоки, ожидания, CPU и I/O.
3. Отрицательные тесты ложных связей.
4. Права обычного пользователя и привилегированного helper.
5. Реальные действия в интерфейсе RU/EN.
6. DPI и отзывчивость Qt.
7. Большие индексы и стресс обработки 250 000 событий.
8. Старые и новые сеансы, Trace Decoder и BB-DEEP-001 без регрессий.
9. Полная сборка portable EXE.
10. Maintenance/update/uninstall и проверка финального ZIP.

**Повторный тест 5 часов 30 минут не является обязательным для BB-INV-003**, поскольку основной объём патча — чтение и корреляция сохранённых данных.

Если Codex изменит механизм непрерывной записи, жизненный цикл sampler/helper или управление системными ресурсами, необходимость длительной проверки должна определяться затронутыми рисками.

Ни один обязательный тест не запускать на пользовательском компьютере.

## 16. Что не входит в текущий патч

Чтобы не превращать BB-INV-003 в бесконечную разработку, отделить от обязательной приёмки:

- Полноценную копию Process Monitor, включая полный захват реестра.
- Отладчик масштаба WinDbg с полной поддержкой его расширений.
- Универсальный разбор managed heap и графа удержания объектов.
- Полное автоматическое определение причин по произвольному дампу.
- Поддержку всех вариантов WOW64/ARM64/JIT/PDB.
- Облачную систему отслеживания ошибок уровня Sentry.
- Полный графический конструктор пользовательских автоматизаций.
- Обязательное AI/LLM-заключение о причине проблемы.

Однако новые контракты должны позволять подключать эти возможности в будущем.

## 17. Критерии готовности

Патч считается готовым к интеграции, если:

- Создан рабочий граф диагностических доказательств.
- Связи имеют проверяемые источники и точные классы достоверности.
- Реализован частичный Critical Path Analyzer.
- Гипотезы разделены на подтверждённые наблюдения и предположения.
- Пользователь может перейти от гипотезы к реальному доступному диагностическому действию.
- Группируются повторяющиеся проблемы без ложного объединения.
- Реализовано сравнение сопоставимых запусков разных версий.
- Всё находится внутри существующего интерфейса Overview.
- Старые отчёты и Investigation Engine 2 продолжают работать.
- Новые операции не нарушают безопасность и жизненный цикл BB-DEEP-001.
- Отсутствующие данные и неподтверждённые связи не подменяются правдоподобными результатами.
- Есть RU/EN документация, тесты, технический отчёт и реальные evidence.
- Пройдены все обязательные GitHub-hosted CI.
- Независимый review не выявил незакрытых блокирующих дефектов.

Публикация Release требует отдельного разрешения владельца.

## 19. Главный принцип проекта после BB-INV-003

**BLACK.BOX не должен быть просто программой, которая показывает, что произошла ошибка.**

Он должен стать инструментом, позволяющим пользователю последовательно исследовать её:

**Обнаружить → Связать доказательства → Построить гипотезу → Выбрать инструмент → Проверить → Сравнить результат.**

Пользователь управляет глубиной исследования и разрешениями. BLACK.BOX предоставляет реальные диагностические возможности Windows, объясняет последствия вмешательства и сохраняет различие между наблюдением, предположением и установленным результатом.

**Цель патча — не увеличить количество показателей, а сделать уже собранные данные практически полезными для поиска причин проблем.**
