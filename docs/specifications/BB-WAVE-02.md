## Большая партия разработки для CODEX: R20 + R30 + R40 + R50

**Проект:** BLACK.BOX Universal  
**Репозиторий:** https://github.com/jumonja-maker/BlackBox-Rep.-Alva-/  
**Тип работы:** четыре крупных взаимосвязанных функциональных контейнера с единой сквозной приёмкой.

## ГЛАВНАЯ ЗАДАЧА

Развить BLACK.BOX до полноценного цикла расследования:

**Обнаружение проблемы → сбор настоящих данных → проверка доказательств → расследование зависания или аварии → повторный эксперимент → сравнение → проверяемый отчёт → сохранение → повторное чтение → безопасное завершение.**

Это одна большая инженерная волна, а не 34 независимых мелких патча.

Главное правило владельца:

**Если BLACK.BOX технически умеет выполнить поддерживаемую операцию и Windows её разрешает, программа обязана действительно выполнить её, а не просто сообщить «не могу».**

При недостатке прав используется существующий R10 Diagnostic Helper с управляемым UAC. Нельзя обходить системные ограничения, повышать весь GUI или проводить вмешательства без отдельного подтверждения.

Не создавать новые копии существующих Decoder, Evidence Graph, Investigation Engine 3, Deep Inspection или административного Helper. Развивать уже работающие механизмы.

# КОНТЕЙНЕР R20 — ДОСТОВЕРНОСТЬ ДОКАЗАТЕЛЬСТВ И ЖИЗНЕННЫЙ ЦИКЛ

**Цель:** обеспечить надёжное происхождение данных, безопасное выполнение операций, восстановление после ошибок и сохранность результатов от первичного сбора до повторного чтения.

### Задачи R20

**R20-01. Инвентаризация существующих механизмов.** Изучить `evidence_graph.py`, `evidence_correlation.py`, `deep_tool_contracts.py`, `deep_journal.py`, `session_v2.py`, `session_completion.py`, `trace_recovery.py` и Investigation Engine 3. Определить реальные разрывы, не переписывая уже работающий функционал.

**R20-02. Идентичность источника.** Каждая доказательная запись должна по возможности иметь source ID, тип, размер, SHA-256, происхождение и статус доверия. Импортированная JSON-запись не становится аутентифицированной только из-за правильного формата.

**R20-03. Идентичность процессов и потоков.** Использовать точный экземпляр процесса — PID + creation FILETIME, контекст запуска и доступные подтверждённые идентификаторы потока. Не связывать старую трассу с новым процессом лишь по совпавшему PID.

**R20-04. Временные области.** Корректно различать UTC, monotonic timestamps, ETW clocks, время сеанса и погрешность сопоставления. Не заменять неопределённость выдуманной синхронизацией.

**R20-05. Полнота данных.** Фиксировать пропуски, потери, ограничения времени и памяти, неполные источники и недостающие участки наблюдения. `INCOMPLETE` не должен превращаться в `COMPLETE`.

**R20-06. Безопасное сохранение.** Усилить атомарное сохранение SQLite/JSON/HTML, защиту от перезаписи существующих файлов, проверку хешей и независимое повторное чтение результата. Никакой порчи пользовательских исходников при ошибке экспорта.

**R20-07. RunReceipt и фактическое выполнение.** Использовать существующие R10 `ToolDescriptor`, `RunContext`, `RunReceipt`. Подключить необходимые адаптеры к реальным вызовам Decoder, Deep и Investigation, не создавая второй контрактный движок.

**R20-08. Владение ресурсами.** Проверить совместную работу ETW/WPR, debugger, Diagnostic Helper, writer и файловых ресурсов. Одна диагностика не должна завершать чужую ETW-сессию или освобождать ресурсы другого владельца. Неизвестная очистка должна сохранять `RECOVERY_UNCONFIRMED`.

**R20-09. Интеграция и восстановление.** Протестировать повреждённый импорт, отмену, тайм-аут, завершение процесса, сбой writer, конфликт ресурсов и ошибку экспорта. Реализовать полный путь от первичного источника через Decoder и Investigation до отчёта, read-back и подтверждённой очистки.

**Критерий завершения R20:** один реальный Windows E2E подтверждает происхождение, идентичность, полноту, сохранение, отсутствие повреждения исходников и правильное освобождение ресурсов. Все применимые обязательные CI-проверки проходят на точном SHA.

# КОНТЕЙНЕР R30 — ГЛУБОКОЕ РАССЛЕДОВАНИЕ ЗАВИСАНИЙ И I/O

**Цель:** дать пользователю возможность находить реальные наблюдаемые причины задержек приложения, когда данные это позволяют, и явно обозначать `UNKNOWN`, когда причинная связь не установлена.

### Задачи R30

**R30-01. Единая картина ожиданий.** Связать существующие Windows WCT, `decoder_waits.py`, `critical_path.py`, CSwitch, ReadyThread, scheduler observations и Evidence Graph.

**R30-02. UI Freeze и Wait Chain.** Реализовать законченный сценарий наблюдения зависшего UI-потока, ожидания mutex/event, задержки планировщика и возвращения потока к выполнению.

**R30-03. Подтверждение владельца блокировки.** Не приписывать блокировку другому потоку только по времени или имени. Владельца указывать исключительно при достаточной подтверждённой информации Windows.

**R30-04. FileIO.** Улучшить фактическую диагностику файловых операций: `ACCESS_DENIED`, sharing violation, ошибки чтения/записи, NTSTATUS, Win32 error, реальные durations и ограничение доступных данных.

**R30-05. DiskIO.** Добавить подтверждённые задержки операций и очереди там, где исходные ETW-события действительно позволяют их рассчитать. Не превращать общий счётчик диска в latency конкретного запроса.

**R30-06. Сеть.** Интегрировать доступные сетевые метаданные, состояния соединений и ошибки с точным экземпляром процесса. Не читать чужие payload и не делать необоснованный вывод, что причиной задержки была сеть.

**R30-07. Связь с Investigation.** Объединить подтверждённые thread/process/module/stack/file evidence, Critical Path и Hypotheses. Пользователь должен видеть источники, на основании которых сформирован вывод.

**R30-08. Настоящие Windows-фикстуры.** На GitHub-hosted Windows реализовать controlled tests для mutex wait, UI freeze, file lock, denied access и других доступных сценариев. Отдельно создать отрицательные контроли с нерелевантными событиями, переиспользованным PID и потерянными ETW-данными.

**R30-09. Пользовательский интерфейс и отчёт.** Сделать реальный путь: выбрать процесс → собрать доступные данные → исследовать задержку → открыть Evidence Graph/Critical Path → получить JSON/HTML → повторно прочитать доказательства. При нехватке прав предложить поддерживаемый R10 Helper, а не заглушку.

**Критерий завершения R30:** подтверждены фактические ожидания и ошибки I/O на собственных тестовых процессах. Программа не выдумывает владельцев блокировок и причины задержек. Работают GUI, экспорт, read-back и cleanup.

# КОНТЕЙНЕР R40 — CRASH, WER, ДАМПЫ И ПАМЯТЬ

**Цель:** дать пользователю законченный маршрут расследования аварийного завершения, от события Windows до доступных сведений о процессе, модулях и памяти.

### Задачи R40

**R40-01. Использовать действующие компоненты.** Изучить и расширить `crash_events.py`, `deep_dump.py`, `deep_native_stacks.py`, Deep Inspection, Decoder и Investigation Engine 3. Не создавать собственный универсальный WinDbg.

**R40-02. Windows Event Log и WER.** Корректно получать доступные события аварий и завершения процесса. Не путать PID процесса, записавшего событие, с PID аварийного приложения.

**R40-03. Точная привязка аварии.** Связать событие, время, версию образа, экземпляр процесса, модуль и доступные снимки «до/во время/после» только при достаточных основаниях.

**R40-04. Надёжный Minidump.** Подтверждать формат, размер, streams, SHA-256, модули, диапазоны памяти и ограничения файла. Неполные, повреждённые или слишком большие дампы должны обрабатываться безопасно.

**R40-05. Нативные стеки.** Улучшить анализ AMD64 stack frames, сопоставление модулей, PDB и поддерживаемых символов. Различать реально подтверждённую строку исходника и предположительное имя функции.

**R40-06. .NET/Managed источники.** Разбирать доступные CLR/EventPipe/.NET данные, если источник действительно поддерживается. Не обещать универсальный анализ managed heap, если он не реализован.

**R40-07. Crash Investigation в GUI.** Сделать связанный просмотр события, дампа, модулей, стеков и доказательств с экспортом JSON/HTML. Дампы и байты памяти не должны автоматически попадать в обычный публичный отчёт.

**R40-08. Реальная и отрицательная QA.** Проверить намеренную аварию собственного Windows-приложения, обычное завершение без аварии, повреждённый дамп, отсутствующие символы, недоступный WER, отказ доступа, отмену и повторное чтение результатов.

**Критерий завершения R40:** на контролируемой аварии BLACK.BOX показывает реально наблюдаемые сведения и их источники. При отсутствии данных не выдумывает root cause. Приватность, сохранение и очистка подтверждены тестами.

# КОНТЕЙНЕР R50 — РЕДКИЕ ИНЦИДЕНТЫ И ПОВТОРЯЕМЫЕ ЭКСПЕРИМЕНТЫ

**Цель:** позволить пользователю поймать кратковременную неисправность, сохранить ограниченную предысторию и корректно сравнить повторения.

### Задачи R50

**R50-01. Использовать существующую основу.** Развивать `incidents.py`, `experiments.py`, `experiment_metrics.py`, `research_worker.py`, `user_markers.py`, capture profiles и Investigation 3.

**R50-02. Ограниченная предыстория.** Реализовать или усилить bounded pre-incident buffer с явными ограничениями количества событий, памяти, времени и диска. Потери должны отражаться в coverage, а не скрываться.

**R50-03. Триггеры событий.** Поддержать доступные CPU bursts, рост потребления памяти, UI freeze, crash marker, I/O bursts и ручную отметку проблемы пользователем.

**R50-04. Incident Burst.** Сохранять реальные события до, во время и после инцидента в рамках измеренного бюджета. Проверять overhead, backpressure и восстановление записи без потери исходных сеансов.

**R50-05. Контролируемые эксперименты.** Пользователь вручную запускает исследования ДО/ДЕЙСТВИЕ/ПОСЛЕ. Сохраняются run ID, версия приложения, build/image hash, нагрузка, профиль измерения и точный экземпляр процесса.

**R50-06. Сопоставимость повторений.** Различать сравнимые и несравнимые эксперименты. Разные версии, нагрузка, неполные данные, потерянные часы и отсутствующие сенсоры должны давать `NOT_COMPARABLE` или `INCONCLUSIVE`, а не фиктивное «исправлено».

**R50-07. Исследования в Investigation 3.** Сделать полезный просмотр повторных попыток, реальных метрик, интервалов, статистических ограничений, гипотез и источников. Экспорт и повторное чтение обязательны.

**R50-08. Реальные испытания.** Воспроизвести редкое контролируемое событие, отсутствие события, разные уровни нагрузки, повторение с другим экземпляром процесса, потерю части предыстории, ошибку остановки и ограничение retention. Измерить накладные расходы. Если меняется sampler/lifecycle — выполнить соответствующий длительный endurance-тест по риску.

**Критерий завершения R50:** программа действительно сохраняет ограниченную предысторию, позволяет повторять и сравнивать исследования и правильно отражает неопределённость результатов.

Построить один реальный end-to-end маршрут на принадлежащих тесту Windows x64 приложениях:

**Сценарий A — зависание:** контролируемый mutex/UI wait и файловая ошибка.

**Сценарий Б — авария:** собственный процесс аварийно завершается; проверяются доступные Event Log/WER/minidump/stack evidence.

**Сценарий В — редкий инцидент:** контролируемый всплеск CPU/I/O/памяти, захват предыстории и несколько повторных экспериментов.

**Сценарий Г — отрицательный контроль:** нерелевантное событие, другой экземпляр процесса, неполный источник, потеря ETW или ошибка доступа.

Для каждого применимого сценария пройти цепочку:

1. Реальный собственный процесс / источник Windows.
2. OBSERVE, R10 Helper или ETW только в допустимом режиме.
3. Сохранение сессии и идентичности источника.
4. Декодирование и проверка доказательств.
5. R30 либо R40 Investigation.
6. Связанный Evidence Graph и допустимые Hypotheses.
7. R50 повторение/сравнение, если применимо.
8. Экспорт JSON/HTML, независимый read-back и подтверждённый cleanup.

Если одна часть цепочки технически недоступна, указать точную причину и доступный рабочий альтернативный маршрут. Не подменять реальный результат моками.

# ОБЯЗАТЕЛЬНОЕ QA

**Все автоматические тесты и сборки выполнять исключительно на стандартных бесплатных GitHub-hosted Windows/Linux runners.**

Никаких локальных VM, пользовательского ПК, платных runners, self-hosted машин или передачи результатов через GitHub Actions Artifacts.

Использовать существующее полное CI-покрытие, включая четыре группы Windows unit-тестов, настоящие Windows native/GUI/ETW, Linux compatibility и полный Windows Portable EXE.

Для каждого контейнера требуется:

- Реальный положительный сценарий с подтверждённым результатом.
- Отрицательные сценарии и fault injection.
- Проверка прав, точной цели, отмены и владения ресурсами.
- Интеграция с другими реально затронутыми компонентами.
- GUI RU/EN/DPI при изменении интерфейса.
- Экспорт, проверка сохранения и независимый read-back.
- Cleanup, no-clobber и защита пользовательских исходников.
- Полный набор обязательных SUCCESS на одном точном SHA.

`FAILED`, `CANCELLED`, обязательный `SKIPPED` или `NOT RUN` не являются PASS.

Не переносить зелёный CI с предыдущего SHA на новый. Не сокращать покрытие ради скорости.

Физические UAC Secure Desktop и Windows 10/11, не доступные на hosted runners, отмечать `NOT_TESTED`. Не требовать этих тестов на домашнем компьютере владельца.
